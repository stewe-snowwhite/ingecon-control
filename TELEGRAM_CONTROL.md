# Дозвіл Start/Stop через Telegram

Бот підтримує реальні команди через спільний `commands.py` для Administrator
і Operator після двоетапного підтвердження. Viewer не керує інверторами.
Статуси та історія, як і раніше, читаються лише з SQLite; фонових ICMP/TCP/Modbus
перевірок бот не запускає. Вебпанель залишається з `MODBUS_WRITES_ENABLED=False`.

## Межа між реалізацією та активацією

Підготовка коду та автоматичні тести не виконують фізичних записів, не змінюють
production SQLite, користувачів, прив’язок, токена, SECRET_KEY чи systemd.
Не запускається другий бот. Чинний polling не зупиняється й не перезапускається.

Без `INGECON_TELEGRAM_CONTROL_CONFIG` бот працює з повністю заблокованими
пристроєвими транспортами. Для активації потрібен окремий захищений файл із
переліком дозволених пристроїв та **підтвердженою для кожної моделі картою**.
Успадковані регістр 1000 і значення 6/5 не є перевіреною картою виробника
та не підставляються автоматично. Профіль читання монітора не дає дозволу запису.

Поки моделі й карти не надано, production-конфігурація керування не створюється.
Сам запит дозволити керування не визначає правильні адреси/значення регістрів.

## Формат конфігурації

Шлях рекомендовано `/opt/ingecon-control/instance/telegram/control.json`;
власник — користувач служби (`codex` у поточному unit), права 0600.
Символічні посилання, загальний доступ, невідомі поля, повтори JSON-ключів,
дублі ID/пристроїв, некоректні числа й непідтверджені карти відхиляються.
Розмір обмежено 32 KiB, кількість записів — 100.

Безпечна вимкнена конфігурація:

```json
{"enabled": false, "inverters": []}
```

Для дозволу встановлюється `enabled: true`, а `inverters` містить записи:

| Поле | Значення |
|---|---|
| `id` | Наявний ID інвертора з production SQLite; позитивне ціле |
| `ip` | Точна IP-адреса цього інвертора, без hostname |
| `model` | Точна модель із документації виробника, 1–100 символів |
| `port` | Підтверджений TCP-порт, 1–65535 |
| `device_id` | Підтверджений Modbus unit ID, 1–255 |
| `register_map_confirmed` | `true` лише після перевірки карти конкретної моделі |
| `start` | Об’єкт `{"address": N, "value": N}` для Start |
| `stop` | Об’єкт `{"address": N, "value": N}` для Stop |

`address` — нульова адреса протоколу (0–65535), а не позначення виду 4xxxx;
`value` — ціле 0–65535. Підтримується тільки одиночний запис **FC06** із
підтвердженням відповіді та наступним читанням **FC03**. Якщо конкретна модель
потребує FC16, unlock-послідовності, іншої адресації або не дозволяє читати
командний регістр, для неї спочатку потрібен відповідний адаптер.
Жодних робочих номерів регістрів у цьому документі не вигадано.

Програма перевіряє форму конфігурації, але не може перевірити правильність
карти виробника за її JSON-полями. Модель та семантику має підтвердити власник
обладнання за документацією до фактичного ввімкнення.

## Перевірка конфігурації без мережі

Виконати від користувача служби в корені проєкту:

```bash
.venv/bin/python telegram_bot.py check-control-config --file /opt/ingecon-control/instance/telegram/control.json
```

Команда не відкриває БД, не потребує токена, не викликає Telegram API чи Modbus.
Вона показує тільки стан дозволу та кількість пристроїв. Невалідний файл
завершує перевірку з помилкою; його не слід підключати до працюючої служби.
Файл читається лише при запуску: оновлення потребує погодженого restart.

## Активація на сервері — після перевірки моделей і дозволу на restart

Потрібен root; пароль у чат не передається. Спочатку підготуйте фактичний
перевірений JSON поза Git. Не перезаписуйте наявну конфігурацію без її backup.
Наступні команди призначені для першої активації, коли файли ще не існують;
`/root/verified-inverter-controls.json` — файл власника з реальними перевіреними даними.

```bash
set -eu
cd /opt/ingecon-control
test ! -e /opt/ingecon-control/instance/telegram/control.json
test ! -L /opt/ingecon-control/instance/telegram/control.json
test ! -e /etc/systemd/system/ingecon-telegram.service.d/20-controls.conf
test ! -L /etc/systemd/system/ingecon-telegram.service.d/20-controls.conf
install -o codex -g codex -m 0600 /root/verified-inverter-controls.json /opt/ingecon-control/instance/telegram/control.json
runuser -u codex -- /opt/ingecon-control/.venv/bin/python telegram_bot.py check-control-config --file /opt/ingecon-control/instance/telegram/control.json
install -d -m 0755 /etc/systemd/system/ingecon-telegram.service.d
cat > /etc/systemd/system/ingecon-telegram.service.d/20-controls.conf <<'EOF'
[Service]
Environment=INGECON_TELEGRAM_CONTROL_CONFIG=/opt/ingecon-control/instance/telegram/control.json
EOF
systemctl daemon-reload
```

Ці команди не змінюють токен, основний unit, БД, writable-шляхи, Nginx,
Tailscale, firewall чи SSH. Чинний бот поки використовує попередні налаштування.
Після окремого дозволу на перезапуск **наявного одного екземпляра**:

```bash
systemctl restart ingecon-telegram.service
systemctl is-active ingecon-telegram.service
systemctl is-enabled ingecon-telegram.service
```

Ручний `telegram_bot.py run` паралельно не запускають. Блокування за bot ID
та production SQLite залишено. Зупинка й заміна старого процесу належать systemd.
Для повторного блокування підготуйте `enabled:false`, `inverters:[]`, перевірте
файл і погодьте restart цієї ж служби. Це не відкликає вже переданий запис
і не гарантує скасування команди, яка вже виконується.

## Поведінка команд

`/control` → інвертор/група → Start/Stop → точні ID/назви/IP → підтвердження.
До підтвердження записів немає. Для групи всі цілі мають бути дозволені;
якщо хоча б один ID/IP відсутній у конфігурації, записів для всієї групи немає.
Зміна IP, прав, версії сесії, складу групи або політики анулює старий preview.
Старий preview, створений при вимкненому керуванні, не стає дозволеним після ввімкнення.

Перед I/O SQLite атомарно зберігає `processing` і звільняє транзакцію.
Виконання працює в допоміжному потоці, не блокуючи Telegram event loop
та доставку сповіщень. Нові updates і надалі обробляються послідовно.
Повторне/одночасне підтвердження не може повторити команду. Спільний файловий
lock за IP/портом зберігає взаємне виключення з монітором і іншими операціями.
Запис і readback виконуються без автоматичних retries. Кожна ціль має результат:
`register_confirmed` або `unconfirmed`; загалом — `confirmed`, `partial`,
`unconfirmed`, `blocked`, `cancelled`, `expired`, `invalidated` або `unknown`.

Підтвердження регістра **не підтверджує фізичний стан**. При таймауті,
втраті відповіді чи падінні процесу результат може бути невідомим, навіть якщо
запис відбувся. Після restart незавершені `processing` стають `unknown`;
автоматичного повторення немає. Якщо audit commit після I/O не вдався,
intent залишається спожитим; бот повідомляє про можливий невідомий результат.
Спочатку перевіряють стан обладнання, а потім вирішують щодо нової команди.

Аудит зберігає Telegram ID, користувача, час, дію, цілі, модель, порт/unit ID,
фактичну адресу/значення команди й результати без секретів.
Початкова реалізація дозволяє тільки Start/Stop; ліміти потужності через бот
не додаються. Статуси та сповіщення продовжують працювати незалежно від дозволу.

## Тести

```bash
.venv/bin/python -m pytest -q
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
```

Усі карти та Modbus-записи в тестах — mock; фізична мережа заблокована.
Перевіряються ролі, явний дозвіл, карта/ID/IP, груповий preflight, невдала
відповідь, readback, одноразовість, паралельні callback, аварійне завершення,
відновлення audit, відсутність DB lock під час I/O та збереження статусів/сповіщень.
