# TASK-03: фоновий моніторинг

## Тимчасовий інтервал опитування

На головній сторінці адміністратор може задати спільний інтервал від **1 до 86400 с**
на **30 хвилин**. Він змінює реальне read-only опитування зареєстрованих інверторів
і частоту оновлення вебпанелі. Після серверного строку дії відновлюється **30 с**,
навіть якщо вкладка закрита або монітор перезапускався. Схема SQLite не змінюється.
Фактичний період за повільних відповідей обмежений тривалістю послідовного циклу;
пропущені цикли не накопичуються й не запускаються паралельно.
Деталі, тести й погоджене застосування: [MONITOR_POLLING.md](MONITOR_POLLING.md).

## Телеметрія INGECON SUN 100TL

Для підтвердженої моделі `ingecon_sun_100tl` профіль `ingecon_100tl_input`
вибирається автоматично в усіх процесах незалежно від IP. Модель обирає
Administrator у формах додавання/редагування. Невідома модель лишається
`unknown`: їй профіль автоматично не призначається. Порт і Unit ID залишаються
індивідуальними транспортними параметрами; зміна моделі їх не переписує.
Результат discovery сам по собі не є доказом моделі.

FC04 читає лише блоки 20–35 (16 слів) та 52–54 (3 слова), без повторів.
Два повні блоки підтверджено на `192.168.1.12:502`, Unit ID 1, 21.10.2026.
Читання не виконується вебсторінкою або API: вони показують останній знімок БД.

`inverter_status` зберігає `operating_state_code` (Input 20), `active_power_raw`
та `active_power_w` (Input 29, signed Int16 × 10 W), `power_limit_percent`
(Input 52, 0–100%) і `limit_reason_code` (Input 53). Потужність на панелі
показується в кВт; raw `6298` означає `62980 W` = `62,98 кВт`.
Код робочого стану `2` показується як «Підключений до мережі».
Для інших кодів стану/причини зберігається числовий код без вигаданого пояснення.
Код причини `0` не приховується як порожнє значення.

Робочий стан відокремлено від доступності `Online/Offline/Degraded/Unknown`.
Чинний гістерезис (дві успішні/три невдалі Modbus-перевірки) не змінено;
невдалий ICMP не заважає `Online`. Застарілі, відхилені або неповні читання
не показують стару телеметрію як актуальну. Записується лише поточний знімок;
історія та Telegram працюють за попередніми змінами доступності.

Для існуючої SQLite потрібна явна адитивна міграція з перевіреною online backup.
`init-db` не додає колонки до наявних таблиць. Порядок контрольованої активації,
перевірки й відкату: [TELEMETRY_DEPLOY.md](TELEMETRY_DEPLOY.md).

Окремо додано явний read-only профіль `ingecon_100tl_input` для ABS1004:
FC04 читає лише 20–35 та 52–54; Input 52 дає поточний ліміт 0–100 %.
Для явно позначеної моделі `ingecon_sun_100tl` профіль обирається автоматично;
невідомі моделі автоматично його не отримують. Старі транспортні налаштування
не переписуються.
Джерело карти, відмінність від історичних Holding-команд і правила підготовки:
[MODBUS.md](MODBUS.md). Енергетичних лічильників або стрінгів він не опитує.

TASK-04 розширює панель і цей API лічильниками, пошуком, автооновленням та
історією, зберігаючи правила монітора. Ручні перевірки й далі ставлять запит
на наступний цикл; видалення тепер потребує підтвердження.
Деталі: [DASHBOARD.md](DASHBOARD.md).

## Архітектура та межі цього етапу

`monitor.py` — окремий синхронний Python-процес. Він не запускає Flask-сервер,
не імпортує `app.py` і не потребує секрету вебсесій. Використовує наявну SQLite-БД
та спільні моделі. `monitoring.py` містить незалежні перевірки, правила переходів
і формування знімка станів із БД. `operation_locks.py` серіалізує підключення
між процесами та потоками.

Панель `/` і `GET /api/statuses` читають показники з БД та параметри інтервалу з
приватного файла. Відкриття сторінки або API
не створює Modbus-клієнта, не виконує ping чи TCP connect. Авторизація, ролі,
CSRF, сесії та обмеження входу TASK-02 збережені. Modbus-записи залишаються
заблокованими за замовчуванням; у моніторі немає операцій запису регістрів.

Під час реалізації виконувались лише тести на mock та синтетичних SQLite-БД.
Робоча БД не відкривалась для міграцій, фоновий процес із реальними адресами
не запускався. Нові системні пакети не встановлювались. Systemd, firewall,
SSH і Nginx не змінювались. Telegram-повідомлення не надсилались.

## Профіль читання для кожного інвертора

Не існує універсального безпечного Modbus-регістра для всіх моделей.
За замовчуванням `read_address=NULL`: монітор може перевірити ICMP і TCP,
але не виконує Modbus-читання та залишає стан `Unknown`.

Для INGECON SUN 100TL достатньо вибрати модель у вебформі. Інші явні профілі
задаються локально через Flask CLI, без мережевих підключень.
Потрібно перевірити за документацією конкретної моделі:

- IP, TCP-порт і Modbus device ID;
- адресу початкового holding-регістра у нульовій адресації протоколу;
- дозволену кількість регістрів для FC03;
- чи придатне саме це читання для перевірки справності пристрою.

Порт: 1–65535, device ID: 1–255, кількість: 1–125; діапазон адрес не може
виходити за 0–65535. Приймаються IP-літерали; loopback, multicast та unspecified
відхиляються. Некоректні налаштування не запускають жодної перевірки.
Загальний профіль `generic` підтверджує валідність відповіді, але не інтерпретує
регістри як фізичний стан чи потужність.

`legacy_ingeteam` — явно вибраний профіль для успадкованого читання двох
регістрів від адреси 1000. Лише цей профіль показує відсоток ліміту: якщо
перший регістр дорівнює 16, другий у межах 0–32767 масштабується до 0–100%.
Він **не підтверджений для фізичного обладнання** і не обирається автоматично.
Використання потребує перевіреної карти саме вашої моделі.

## Підготовка схеми та майбутній запуск

Ці кроки документують майбутнє введення в експлуатацію; вони не виконувались
під час TASK-03. Мережеве опитування реальних інверторів потребує окремого
погодження. Перед будь-якою зміною production-схеми потрібна перевірена
узгоджена резервна копія SQLite, включно з урахуванням WAL. Звичайне копіювання
одного файла активної БД може бути недостатнім; використовуйте SQLite backup
API або погоджене зупинення користувачів БД.

1. Зробити резервну копію та перевірити її читання на окремій копії.
2. Надати вебзастосунку `INGECON_SECRET_KEY` та той самий `INGECON_DATABASE_URI`,
   який використовуватиме монітор. Правила секрету: [SECURITY.md](SECURITY.md).
3. Явно додати відсутні таблиці:

   ```bash
   .venv/bin/python -m flask --app app init-db
   ```

   `create_all()` додає таблиці `monitor_config`, `inverter_status`,
   `state_event`, `monitor_heartbeat`; структури наявних `inverter`, `user`
   та `login_throttle` не змінюються. Це не система версійних міграцій.
   Монітор сам таблиць не створює: без підготовленої схеми завершується до
   мережевого опитування. Перед оновленням вебпроцесу схема також має бути
   підготовлена: нові маршрути читають ці таблиці.
4. Після перевірки карт регістрів задати профілі. Нижче `INVERTER_ID`,
   `DEVICE_ID`, `READ_ADDRESS`, `READ_COUNT` — позначення підтверджених значень,
   які слід замінити перед виконанням:

   ```bash
   .venv/bin/python -m flask --app app configure-monitor INVERTER_ID --port 502 --device-id DEVICE_ID --read-address READ_ADDRESS --read-count READ_COUNT --profile generic
   ```

   Команда тільки зберігає налаштування. Не переносіть адресу 1000 на інші
   моделі без перевірки документації. Для `legacy_ingeteam` необхідні
   `--read-address 1000 --read-count 2` і окреме підтвердження цього профілю.
5. Забезпечити однаковий OS-користувач і каталог блокувань вебпроцесу та
   монітора. За замовчуванням це `instance/locks` у корені проєкту;
   `INGECON_LOCK_DIR` може задавати спільний абсолютний шлях.
6. Лише після погодження реального читання запустити процес у передньому плані:

   ```bash
   .venv/bin/python monitor.py --interval 30 --timeout 2
   ```

   Зупинення: SIGINT/Ctrl+C або SIGTERM. Процес завершує поточну обмежену
   таймаутами перевірку, записує `stopped=True` і виходить. Systemd unit
   на цьому етапі не створюється і не активується.

`--database-uri` / `INGECON_DATABASE_URI` за замовчуванням:
`sqlite:///database.db`. Відносний SQLite-шлях тлумачиться від каталогу
`instance` проєкту, як у Flask-SQLAlchemy. Абсолютний URI, наприклад
`sqlite:////absolute/path/database.db`, має бути однаковим у всіх процесів.
Окремий монітор приймає тільки файлову SQLite-БД, яка вже існує.

`--interval` / `INGECON_MONITOR_INTERVAL`: 1–86400 секунд, типово **30**.
`--timeout` / `INGECON_PROBE_TIMEOUT`: 0.1–10 секунд, типово **2** на окрему
мережеву операцію. Параметри CLI мають пріоритет над змінними середовища.
`--once` виконує один цикл і позначає монітор зупиненим; після виходу ефективні
статуси API будуть `Unknown`, а результат циклу залишиться у `recorded_state`.
Безпечний перегляд аргументів, який не опитує інвертори:

```bash
.venv/bin/python monitor.py --help
```

## Незалежні перевірки

| Перевірка | Як працює | Що означає результат |
|---|---|---|
| ICMP | Один `ping`, без shell, із subprocess timeout | Діагностика ICMP; відмова не визначає доступність Modbus |
| TCP | Окремий connect до налаштованого порту, потім закриття | Порт приймає TCP-підключення в момент перевірки |
| Modbus | Окремий клієнт, connect та FC03 із перевіркою відповіді | Налаштоване читання конкретного пристрою успішне |

Кожна перевірка виконується незалежно від результатів попередньої. Невдалий
ping або TCP connect не скасовує спробу налаштованого Modbus-читання.
Якщо `ping` відсутній або його виконання не дозволене, ICMP має `ok=null`;
встановлення системного пакета автоматично не відбувається. Для блокованого
ICMP можливий `Online`, якщо TCP і Modbus успішні.

Для кожної перевірки зберігаються `ok=true/false/null`, тривалість та код
помилки. ICMP-тривалість включає запуск subprocess; це не чистий мережевий RTT.
Modbus-тривалість включає встановлення з'єднання та читання. PyModbus працює
із `retries=0`; клієнт закривається у `finally`. Connect і читання — окремі
операції, тому сумарний час перевірки може перевищити один `--timeout`.

Виклик `ping` відповідає [Debian 13 iputils-ping](https://manpages.debian.org/trixie/iputils-ping/ping.8.en.html).
Обмеження subprocess реалізовано через [Python 3.13 subprocess.run](https://docs.python.org/3.13/library/subprocess.html#subprocess.run).

## Правила станів і переходів

Успішний цикл для порога `Online` означає **успішні TCP та валідну відповідь
налаштованого Modbus-читання**. ICMP у цьому порозі не враховується.
Невдалий цикл для порога `Offline` означає **невдалу спробу налаштованого
Modbus-читання**. Невиконана перевірка не рахується як невдача.

| Умова | Поточний стан | Лічильники |
|---|---|---|
| Немає профілю, некоректна конфігурація або Modbus зайнятий іншою операцією | `Unknown` | Обидва пороги скидаються |
| Перша успішна TCP+Modbus перевірка із початкового `Unknown` | `Unknown` | Успіхи = 1 |
| Перша успішна TCP+Modbus перевірка після `Offline` / `Degraded` | `Degraded` | Успіхи = 1 |
| Дві поспіль успішні TCP+Modbus перевірки | `Online` | Успіхи обмежені 2, невдачі = 0 |
| Modbus відповідає, але окрема TCP-перевірка невдала/не виконана | `Degraded` | Обидва пороги скидаються, останній успіх оновлюється |
| Перша або друга поспіль невдала Modbus-перевірка | `Degraded` | Невдачі = 1 або 2 |
| Третя й наступні поспіль невдалі Modbus-перевірки | `Offline` | Невдачі обмежені 3, успіхи = 0 |
| Heartbeat або знімок застарілий, монітор зупинено чи адресу/профіль змінено | Ефективний `Unknown` у вебпанелі/API | Збережений стан лишається у БД |

Будь-яка невдала Modbus-перевірка перериває серію успіхів, будь-яка успішна —
серію невдач. Після перерви між знімками понад три інтервали, зміни цілі або
переведення системного годинника назад пороги накопичуються заново.
При зміні IP/порту/device ID/регістрів/профілю попередній знімок одразу
визнається неактуальним, а його ліміт потужності та час успіху не показуються
як дані нової цілі. Результат запиту, який був у польоті під час редагування
чи видалення інвертора, відкидається при записі.

`Online` означає справність налаштованого читання, а не генерацію енергії.
`Offline` означає три невдалі Modbus-перевірки, а не фізичне вимкнення
інвертора. Зокрема, exception response через неправильний регістр накопичує
невдачі з причиною `modbus_exception_response`; перевірте карту регістрів,
перш ніж трактувати це як мережеву несправність. Якщо TCP і Modbus дають різні
результати, зберігаються обидва; успішний Modbus не стає `Offline` через TCP.

## SQLite, heartbeat та навантаження на Wyse 3040

- `monitor_config`: профіль на інвертор і прапорець запиту ручної перевірки.
- `inverter_status`: один поточний рядок на інвертор, остання спроба,
  останній успішний Modbus-відгук, затримка, причина, пороги й результати проб.
- `state_event`: запис **лише при зміні збереженого стану**, з попереднім
  станом, часом, назвою інвертора, відбитком цілі та причиною. Повторні успішні
  цикли й повторний незмінний `Offline` не додають історію.
- `monitor_heartbeat`: один рядок, ідентифікатор процесу, початок роботи,
  останній heartbeat, інтервал, ознака зупинення, помилка та тривалість циклу.

Відсутній початковий знімок вважається `Unknown`; окрема історична подія
`Unknown → Unknown` не створюється. Видалення інвертора видаляє поточний
знімок і конфігурацію, але зберігає історію та чергу сповіщень із назвою
видаленого інвертора. Штатні таблиці TASK-02 та їх записи збережені.

Монітор опитує пристрої послідовно, без фонового пулу потоків і без черги
необмежених задач. Читальна SQL-транзакція закривається перед мережевими
операціями. Результати пишуться короткими пакетними транзакціями; у швидкому
циклі — один commit на весь цикл зі статусами та heartbeat, а не commit
на кожну пробу. При першому запуску додатково публікується початковий heartbeat.
У довгому циклі результати накопичуються до чергового інтервалу та скидаються
пакетом. Перевірки не тримають SQLite-транзакцію відкритою.

Для інтервалу 30 секунд актуальність heartbeat і кожного знімка — **90 секунд**.
`stopped=True`, відсутній heartbeat, вік понад TTL або від'ємний вік означають
неактивний монітор. Застарілі дані показуються як `Unknown`, з прапорцем
`stale=true` та поясненням. Обчислення цього стану під час HTTP-запиту не пише
у БД й не створює історичних подій. Збережений стан доступний як `recorded_state`.
`last_success_at` залишається історичним часом останнього успішного Modbus-відгуку;
його наявність не робить застарілий знімок свіжим.

За потреби WSGI-конфігурація може передати `MONITOR_STALE_AFTER_SECONDS` у
`create_app(config)`; за замовчуванням TTL визначається з інтервалу heartbeat.
Це налаштування свіжості вебпанелі, а не зміна порогів монітора.

Планувальник намагається починати цикли через заданий інтервал. Якщо цикл
перевищив його, наступний починається після паузи 1 секунда; паралельних циклів
і спроб наздогнати пропущені цикли немає. Для великої кількості недоступних
інверторів повний обхід може перевищити TTL; heartbeat при цьому може бути
актуальним, а ранні знімки — застарілими. Перед production-запуском потрібно
виміряти `cycle_duration_seconds` і підібрати інтервал/таймаути/TTL для реального
парку. Реальне навантаження на Wyse 3040 у TASK-03 не вимірювалось.

Історія не збільшується кожні 30 секунд, але часто змінювані стани все одно
можуть накопичувати події. Автоматичне очищення історії або недоставлених
повідомлень не вводилось, щоб не видаляти наявні дані. Політика зберігання,
архівування та ротації потребує окремого етапу з урахуванням 8 ГБ eMMC.
Повторні однакові помилки циклу не генерують нескінченний потік повідомлень;
PyModbus packet logging у CLI приглушено. Нового файлового журналу монітор
самостійно не створює.

## Блокування конкурентних операцій

Неблокувальний [Linux flock через Python fcntl](https://docs.python.org/3.13/library/fcntl.html)
охоплює всі публічні Modbus-функції застосунку та монітор. Ключ — канонічний
IP + порт, спільний для різних device ID через один шлюз і дубльованих рядків
інверторів. TCP-проба також використовує цей ключ. Зайнята операція повертає
`modbus_busy` / `tcp_busy`, не відкриваючи другого підключення.

Окремий singleton-lock за абсолютним шляхом БД не допускає два монітори
для однієї бази. Каталог створюється з mode 0700, файли — 0600; для файлів
використовується `O_NOFOLLOW`. Файли блокування не видаляються після операції:
видалення inode могло б зруйнувати взаємне виключення між процесами.
Всі процеси та майбутні адаптери повинні використовувати однаковий спільний
каталог і ці обгортки. Інші програми, які самостійно працюють із Modbus,
не підпадають під цей advisory-lock. Блокування не надсилає Modbus write
і не надає дозвіл на керування обладнанням.

## API і ручні перевірки

`GET /api/statuses` доступний Administrator, Operator і Viewer після входу.
Неавторизований запит отримує 401. `?group=...` фільтрує список інверторів.
Відповідь має два ключі:

- `monitor`: `alive`, `last_seen`, `interval_seconds`, `stale_after_seconds`,
  `reason`, `last_error`, `cycle_duration_seconds`;
- `inverters`: ID, назва, група, IP, ефективний `state`, `recorded_state`,
  `stale`, `check_requested`, `checked_at`, `last_success_at`, `latency_ms`,
  `reason`, `power_limit_percent`, незалежні результати у `checks`.

Час API — Unix timestamp у секундах UTC; панель форматує його за `Europe/Kyiv`, автоматично враховуючи літній/зимовий час.
Паролі інверторів, хеші користувачів та секрети сесій у відповідь не потрапляють.
API не викликає мережевих перевірок і не змінює стан БД.

POST `/test/<id>` і `/control` з `action=test` дозволені тільки Administrator
та Operator із чинним CSRF. Вони ставлять `requested_at` у БД і відповідають
«перевірку заплановано на наступний цикл монітора». Це не твердження про
доступність. Плановий цикл і так обходить всі інвертори; ручний запит не
прискорює опитування та не створює додаткової мережевої черги. Прапорець
скидається при збереженні результату. Якщо новий запит надійшов пізніше
часу зібраного результату, він залишається для наступного циклу.

## Основа інтеграції Telegram

TASK-06 споживає переходи через окремі per-recipient курсори й `telegram_delivery`:
одна подія може бути надіслана кільком користувачам без глобального acknowledge.
Legacy `notified_at` збережено для сумісності, але бот його не використовує.
Правила дедуплікації, timeout і повторів: [TELEGRAM.md](TELEGRAM.md).

`state_event` одночасно є історією переходів та outbox. Зміна статусу і подія
зберігаються в одній транзакції, тому майбутньому Telegram-споживачу не потрібно
повторно опитувати інвертори. Для нього передбачено:

- `pending_notifications(session, limit=100)`: недоставлені події за ID,
  обмежена партія 1–1000;
- `acknowledge_notification(session, event_id)`: ідемпотентна позначка доставки
  **після** успішного надсилання; commit виконує споживач;
- `heartbeat_summary(...)`: визначення стану монітора для майбутніх повідомлень
  про його зупинення/застарілість, які не є зміною стану самого інвертора.

Жоден із цих методів не надсилає повідомлень. Бот, токени, адресати, transport
та команда керування не додані. Майбутній споживач має використовувати один
виконавець або механізм claim, дедуплікацію за ID події, обмеження частоти
та обробку накопиченої історії. Після аварії між надсиланням та commit можлива
повторна доставка; це основа для at-least-once, не гарантія exactly-once.

Підготовлене Python 3.13 оточення й залежності описано в [README.md](README.md).
Для TASK-03 нових Python-залежностей немає. Усі перевірки транспорту виконуються
через fake Modbus-клієнт, підставний TCP-контекст та підставний runner для ping.
Autouse-фікстура блокує справжні socket/DNS і subprocess.run. Збої цього захисту
не перетворюються на успішний цикл. Міжпроцесне блокування перевіряється через
Linux fork та OS pipe, без мережі; файли БД і lock-каталоги ізольовані в tmp_path.

Тести перевіряють відмови ICMP/TCP/Modbus, відсутність ping, таймаути, помилки

перезапуск, застарілі дані, зупинення монітора, зміну адреси/профілю,
запити ручної перевірки, відсутність історії для незмінного стану, outbox,
відсутність паралельних операцій і мережевих викликів у вебмаршрутах.
Окремо перевірено додавання таблиць на синтетичну схему TASK-02 зі збереженням
інверторів, облікових даних, ролей, хешів, лімітів входу та працездатного входу.
