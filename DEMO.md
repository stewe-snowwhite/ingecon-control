# TASK-05: ізольований демонстраційний запуск

Демо використовує Flask, маршрути й адаптивні Jinja2-шаблони TASK-04, авторизацію
TASK-02 та формат кешованих статусів TASK-03. Дані, результати перевірок,
затримки й heartbeat тут **вигадані**. На сторінках показано попередження «ДЕМО».
Жоден показник демо не підтверджує стан фізичного інвертора.

## Підготовка без production-даних

Використовуйте наявне Python 3.13 оточення проєкту. Нові залежності для TASK-05
не потрібні. Команди не потребують sudo, встановлення системних пакетів,
налаштування systemd, firewall, SSH або Nginx.

```bash
cd /opt/ingecon-control
.venv/bin/python demo.py init
.venv/bin/python demo.py setup-admin
```

`setup-admin` також виконує первинну ініціалізацію, якщо її ще не було.
Введіть окреме тестове ім’я та новий тестовий пароль двічі. Пароль прихований
під час введення; він не передається аргументом команди й не виводиться.
Ім’я: 1–64 символи `a-z`, `0-9`, `_`, `.`, `-`, із нормалізацією регістру.
Пароль: 12–1024 символи; у БД зберігається salted scrypt-хеш.
Production-паролі, імена та ключі не використовуються й не копіюються.

Стандартного адміністратора або пароля немає. Без активного Administrator
команда `serve` відмовляється відкривати слухач. Повторний `setup-admin` для
того самого імені змінює лише демопароль і відкликає попередні демосесії.
Перед налаштуванням адміністратора потрібно зупинити запущене демо.

Файли створюються в окремому приватному каталозі:

| Файл | Призначення |
|---|---|
| `instance/demo/demo.sqlite` | Інвертори, користувачі, обмеження входів, статуси та історія демо |
| `instance/demo/secret.key` | Окремий випадковий ключ підпису демосесій і CSRF |
| `instance/demo/demo.log` | Вигаданий технічний журнал для перевірки завантаження |
| `instance/demo/demo.lock` | Блокування одночасного запуску процесів із цією демо-БД |

Каталог має права 0700, файли — 0600. `instance/`, SQLite, ключі та журнали
вже виключені з Git. Ключ створюється один раз і зберігається між перезапусками.
Значення `INGECON_SECRET_KEY` та `INGECON_DATABASE_URI` не визначають демоключ
або демо-БД. Імпорт factory більше не створює звичайний застосунок автоматично;
сумісність стандартного WSGI-входу `app:app` збережена.

`instance/database.db` і робочий `modbus.log` не відкриваються для читання або
запису та не мігруються. Перевірка тотожності файлів використовує тільки їхні
метадані. Демо не копіює дані з робочої БД. Наявну SQLite без маркера демо або
з невідповідним ключем відхиляє до запису. Символічні посилання замість
runtime-файлів, неприватні файли та підміна робочою БД/журналом відхиляються.
Звичайний монітор `monitor.py` також відмовляється працювати з демо-маркером
до опитування пристроїв.

Повторний `init` зберігає наявні демоакаунти й зміни інвентарю. Він не скидає
стан до початкового й не перезаписує невідомі файли. Для ще одного незалежного
демо можна додати **перед підкомандою** `--directory /абсолютний/приватний/каталог`;
цей параметр потрібно однаково вказувати для `init`, `setup-admin` та `serve`.

## Локальний запуск у поточному терміналі

```bash
cd /opt/ingecon-control
.venv/bin/python demo.py serve
```

Відкрити: **http://127.0.0.1:5000**. Типова адреса слухача — тільки loopback.
Сервер працює в поточному терміналі без debug, reloader або автоматичного
перезапуску. Не використовуйте `python app.py`, `flask run` чи загальний
WSGI-вхід для демо: повний захист вихідних операцій встановлює саме `demo.py`.
Ввімкнений `FLASK_DEBUG` спричинить відмову запуску; його потрібно вимкнути.

## LAN: 0.0.0.0:5000 та 192.168.10.234

Після інтерактивного створення адміністратора точна команда запуску:

```bash
cd /opt/ingecon-control
.venv/bin/python demo.py serve --host 0.0.0.0
```

Адреса в браузері іншого пристрою: **http://192.168.10.234:5000**.
`0.0.0.0` означає прослуховування всіх локальних IPv4-інтерфейсів; це не адреса
для введення в браузері. Команда передбачає, що `192.168.10.234` уже призначено
цьому комп’ютеру й доступ до порту дозволений наявною мережею. Вона не додає
адресу, не відкриває порт у firewall та не змінює мережевих налаштувань.

У демо дозволені HTTP Host `192.168.10.234`, `127.0.0.1` і `localhost`;
інші значення відхиляються. У режимі `0.0.0.0` також потрібна авторизація;
блокування вихідних підключень залишається чинним. Це окремий HTTP-деморежим
із тестовими обліковими даними для довіреної локальної мережі: HTTP не шифрує
пароль та сесію. Cookie називається `ingecon_demo`, має HttpOnly і SameSite=Lax;
Secure вимкнено **лише в демо** для роботи за HTTP. Production зберігає Secure
та вимогу HTTPS. CSRF, CSP, ролі й обмеження входів залишаються ввімкненими.

LAN-команду підготовлено для ручного запуску. Після останнього уточнення
завдання сервер у фоні не запускався; LAN-слухач під час розробки не відкривався.
Не додавайте `&`, `nohup` чи сервіс автоматичного запуску без окремого дозволу.

## Зупинка

Натисніть **Ctrl+C** у терміналі сервера. Також підтримується SIGTERM конкретному
процесу демо. Процес закриває HTTP-слухач, зупиняє потік імітації, позначає
демо-heartbeat як зупинений і звільняє блокування. SQLite та ключ залишаються
на диску для наступного запуску. Після аварійного завершення heartbeat
застаріє за чинними правилами TASK-03; OS автоматично звільнить flock.
Другий запуск із тією самою БД відхиляється без старту іншого слухача.

## Демонстраційні пристрої та статуси

| Назва | Вигадана адреса | Група | Стан | Імітовані ICMP / TCP / Modbus |
|---|---|---|---|---|
| Демо · Сонячний дах | 192.0.2.10 | Дах | Online | Ні / Так / Так |
| Демо · Віддалена станція | 198.51.100.20 | Поле | Offline | Ні / Ні / Ні |
| Демо · Нестабільний порт | 203.0.113.30 | Поле | Degraded | Так / Ні / Так |
| Демо · Новий пристрій | 192.0.2.40 | Дах | Unknown | Невідомо / Невідомо / Невідомо |

Початкові інвертори не мають логінів, паролів або налаштованого регістра читання.
Адреси — літерали для документаційних прикладів; код до них не підключається.
Випадок Online з невдалим ICMP показує, що ping не визначає доступність Modbus.
Дані й heartbeat оновлюються локально раз на 30 секунд одним легким потоком у
тому самому процесі. Окремий монітор пристроїв не запускається. API читає БД,
як у TASK-03; стабільні цикли не додають історичних подій. При зупинці або
застарілому heartbeat ефективні стани стають Unknown, збережені — залишаються.

Працюють пошук, фільтри груп/станів, автооновлення, теми, історія та CRUD за
ролями TASK-02. Новий або змінений пристрій переходить у Unknown; його не
починають опитувати. Кнопки перевірки лише ставлять локальний запит, який
поглинає наступний цикл імітації. Видалення змінює тільки демоінвентар і
вимагає серверного підтвердження. Результати показуються для кожного пристрою.

## Захист від мережевих операцій

Під час запуску `demo.py` встановлює незнімний у межах цього Python-процесу
audit hook. Він забороняє вихідні `connect`/`connect_ex`, UDP/raw-сокети,
відправлення датаграм, DNS/зворотний DNS, запуск subprocess, exec та fork.
Дозволено лише створення TCP-сокетів для явно вибраного HTTP-слухача
на порту 5000, приймання браузерних запитів і відповіді на них.
Numeric getaddrinfo дозволений лише для адреси/порту цього слухача;
HTTP-сервер не виконує звичайний reverse DNS при bind.

Додатково конструктори Modbus-клієнта та всі реальні NetworkProbes замінені
на функції відмови. Демо не викликає ICMP, TCP або Modbus-перевірок.
`DEMO_MODE` відхиляє start, stop і обмеження потужності з HTTP 403 навіть
при помилковому ввімкненні `MODBUS_WRITES_ENABLED`; відповідні кнопки типово
неактивні. Немає перемикача для дозволу записів у демо. Прямий виклик
низькорівневої команди також не може створити клієнта або мережеве підключення.

Це захист Python-процесу для наявних транспортів застосунку, а не зміна
firewall чи системна ізоляція від довільного стороннього native-коду.
Не підключайте нові транспорти без окремої перевірки блокування.

## Автоматична перевірка без сервера

```bash
cd /opt/ingecon-control
.venv/bin/python -m pytest -q
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
.venv/bin/python -m pip check
```

Лише тести TASK-05:

```bash
.venv/bin/python -m pytest -q tests/test_demo.py
```

Pytest не відкриває HTTP-слухач. Flask test client викликає маршрути всередині
процесу, autouse-фікстура блокує справжні socket/DNS/subprocess.run, Modbus
замінений mock. SQLite, секрети й користувачі створюються тільки в тимчасових
тестових каталогах. CSRF не вимикається. Перевіряються:

- інтерактивне створення/заміна адміністратора, scrypt, cookie й відкликання сесій;
- анонімні запити, Administrator/Operator/Viewer, CSRF і дозволений LAN Host;
- головна, вхід, додавання, редагування, історія, помилки, локальні CSS/JS;
- CRUD, підтвердження видалення, результати й локальна черга перевірок;
- API, усі чотири стани, фільтри, heartbeat, застарілість та відсутність зайвої історії;
- відмова записів навіть з увімкненим прапорцем, блокування транспортів і audit-подій;
- приватні файли, маркер/ключ, підміна файлів, повторна ініціалізація та flock;
- вибір `0.0.0.0` у CLI без реального запуску сервера й відмова звичайного монітора.

Незалежна перевірка встановленого audit hook в окремому Python-процесі:

```bash
.venv/bin/python -m tests.demo_guard_probe
```

Вона створює нез’єднаний TCP-сокет і перевіряє, що спроби connect, DNS,
ping/subprocess та Modbus відхиляються до виконання. Сервер не запускається,
пакети до пристроїв не надсилаються. У sandbox створення навіть такого сокета
може вимагати окремого дозволу; звичайні pytest-тести цього не потребують.

До останнього уточнення завдання також було успішно виконано коротку реальну
HTTP-перевірку на 127.0.0.1:5000 з тимчасовою БД та випадковим тестовим паролем.
Перевірено захищені сторінки, API, ресурси, підтвердження, CSRF і відмову записів;
процес завершився, heartbeat позначено як зупинений. Її сценарій —
`tests/demo_http_smoke.py`; він не входить до pytest й тимчасово запускає дочірній
сервер. **Не запускати його автоматично без дозволу.** Після уточнення адреси
перевірки виконуються без сервера. Візуальна перевірка в браузері не виконувалась.

Підсумкова перевірка TASK-05: **332 Python-тести пройшли**, з них 60 —
деморежиму; xfailed і попереджень pytest немає. **17 JS-тестів пройшли**.
`pip check` та `git diff --check` успішні. Окрема перевірка встановленого
audit hook успішна. Розмір і час зміни робочої БД та журналу залишились
незмінними; пакети й системні налаштування не змінювались.
