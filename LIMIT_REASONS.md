# Причини обмеження потужності 100TL

Головна сторінка показує українську назву з числовим кодом FC04 Input Register 53,
наприклад `Початкове нарощування потужності (10)`. Наведення відкриває коротку
підказку. Невідоме значення: `Невідома причина (код N)`, відсутнє або застаріле: `—`.

Єдиний довідник назв і підказок — `templates/limit_reasons.html`. Його використовує
початковий Jinja HTML, а JavaScript отримує той самий довідник через екранований
атрибут сторінки. API зберігає числовий `limit_reason_code`; Modbus-читання,
керування, таблиці й дані SQLite не змінюються.

Джерело для кодів 0–4: оригінальна карта Ingeteam **AAA0030IMB02_Q**, 03/05/2024,
§7.1, 3Play 100TL/160TL, ABS1004, с. 26–27, Input 53
([публічна копія документа](https://de.scribd.com/document/1045182807/AAA0030IMB02-Q)).
Саме для цієї моделі 0 і 1 мають визначення `Not reduction` («Без обмеження»),
а 2–4 — `Not defined` («Не визначено виробником»). Температурні визначення
з розділів інших моделей не застосовуються. Коди 5–13 відображають погоджені
українські назви; інші коди залишаються числовими з позначкою невідомої причини.

## Перевірки

Виконувати в ізольованій тестовій копії без production-конфігурації:

```bash
.venv/bin/python -m pytest -q tests/test_limit_reasons.py tests/test_telemetry.py tests/test_dashboard.py
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
node tests/js/discovery.test.cjs
```

Тести перевіряють усі коди 0–13, невідомі/відсутні та застарілі значення,
підказки, числовий API, ролі й фактичне автооновлення DOM. Python-фікстури
використовують SQLite in-memory і блокують мережеві підключення; фізичних команд немає.
Результат перевірок цього завдання: 83 Python-тести та 61 JavaScript-тест пройшли.

## Оновлення production

Це інструкція, а не автоматична активація. Нові залежності й міграції не потрібні.
Перед оновленням зберегти перевірену SQLite backup-копію, поточний source/config
snapshot і попередній SHA за чинною процедурою розгортання. Не копіювати активну
SQLite звичайним `cp`, не відновлювати стару БД поверх нових робочих даних.

Переконатися, що потрібний SHA опублікований у GitHub/main. Перевірити відсутність
сторонніх локальних змін. Якщо checkout ще не оновлений, виконати:

```bash
cd /opt/ingecon-control
git status -sb
git fetch origin
git merge --ff-only origin/main
```

Лише під час погодженої активації виконати:

```bash
sudo systemctl restart ingecon-web
```

Перезапуск вебслужби потрібен для скидання кешу Jinja-шаблонів. Моніторинг,
Telegram і discovery worker перезапускати не потрібно. Новий JS підтримує старий
HTML до restart, зберігаючи попереднє відображення числового коду. Після restart
оновити вкладку через Ctrl+Shift+R; перевірити вхід, назву й підказку причини та
їх збереження після автооновлення. Не надсилати команди інверторам для перевірки UI.

Якщо перевірка невдала, повернути файли представлення з перевіреного source snapshot
та повторно перезапустити лише вебслужбу. Не змінювати Modbus-конфігурацію або БД;
не застосовувати `reset --hard`. Після успішної production-перевірки зафіксувати
реліз annotated-тегом і відправити тег на GitHub.
