Публічні маршрути — `/login` і локальні CSS/JS `/static/*` без даних інвентарю.
Неавторизовані запити до бізнес-маршрутів
отримують 401; недостатні права — 403. Невалідний CSRF може спричинити 400 ще
до перевірки ролі. У шаблонах приховано недоступні дії, але перевірка прав завжди
виконується на сервері. `/test/<id>`, `/logout`, видалення й керування дозволені
лише через POST. На `/login` CSRF теж обов’язковий.

Паролі користувачів зберігаються як salted scrypt-хеші Werkzeug. Стандартний
обліковий запис або пароль не створюється. Новий пароль: 12–1024 символи.
Імена користувачів нормалізуються до нижнього регістру, 1–64 ASCII символи
`a-z`, `0-9`, `_`, `.`, `-`. Ролі перевіряються також обмеженням у БД.

Сесія очищається при вході; cookie має Secure, HttpOnly, SameSite=Lax.
Авторизована сесія має строк 30 хвилин без автоматичного продовження при читанні.
На кожному запиті перевіряються активність, актуальна роль і версія сесії у БД.
Зміна пароля або деактивація користувача скасовує попередній доступ.
Вихід збільшує версію сесії та відкликає всі сесії користувача, включно зі
скопійованими cookie. Для роботи cookie потрібний HTTPS; локальні HTTP-тести
використовують внутрішній Flask test client, а не справжній браузер.

У застосунку немає значення секретного ключа за замовчуванням.
`INGECON_SECRET_KEY` має надходити з захищеного зовнішнього середовища й містити
щонайменше 32 символи криптографічно випадкового секрету. Без нього запуск
відхиляється. Зміна ключа відкликає всі підписані сесії. Не зберігайте його в Git,
не передавайте в командному рядку й не використовуйте тестовий ключ.
`DEBUG` за замовчуванням False; factory відхиляє конфігурацію з DEBUG=True та ввімкнений FLASK_DEBUG
(включно з прапорцем Flask CLI --debug).
Не вмикайте налагоджувач через Flask CLI або WSGI-конфігурацію.

Flask-WTF перевіряє CSRF глобально. Форми містять підписані токени;
для запитів JavaScript можна використовувати `X-CSRFToken`. Немає CSRF-exempt
бізнес-маршрутів. За HTTPS також перевіряється same-origin Referer.
Відповіді мають no-store, nosniff, DENY для iframe та обмежувальний CSP для
frame-ancestors, object-src, base-uri і form-action. У TASK-04 вилучено всі CDN,
inline-скрипти, inline-стилі та обробники подій. CSP дозволяє script/style/connect
лише з того самого origin; динамічні значення додаються через DOM/textContent.

## Обмеження спроб входу й журнал

Атомарні SQLite upsert-операції резервують спроби до перевірки пароля:

- максимум 5 спроб на нормалізоване ім’я за 300 секунд;
- максимум 20 спроб на адресу з’єднання за 300 секунд;
- рахуються й успішні спроби, щоб не створювати обхід через скидання ліміту;
- наступні спроби повертають 429 і Retry-After;
- стан зберігається у таблиці `login_throttle`, а не пам’яті вебпроцесу;
- старі прострочені записи очищаються під час входів.

Ліміт спільний між вебпроцесами та зберігається після перезапуску.
Невідомі та неактивні користувачі проходять перевірку dummy scrypt-хешу;
повідомлення про неправильні облікові дані однакове.
Блокування за ім’ям може тимчасово заблокувати легітимного користувача, якщо
хтось цілеспрямовано атакує його ім’я. Це обмеження має бути враховане при
подальшій інтеграції Nginx/Fail2ban.

Logger `ingecon.auth` видає WARNING-події такого формату:

```text
AUTH_FAILURE ip=192.0.2.10 reason=invalid_credentials
AUTH_FAILURE ip=192.0.2.10 reason=rate_limited
```

Паролі, імена користувачів і токени у ці події не включаються. Адреса проходить
валідацію через ipaddress. `X-Forwarded-For` не використовується; без окремо
узгодженої конфігурації trusted proxy за Nginx буде видно адресу проксі.
Поточні повідомлення йдуть через стандартне Python logging у stderr/налаштований
handler. Нові журнали в каталозі вихідного коду не створюються автоматично.
Налаштування їх доставки, ротації та Fail2ban належить наступному етапу;
на цьому етапі systemd і firewall не змінено.

## Керування та блокування Modbus-записів

TASK-04 додає двокрокове серверне підтвердження небезпечних дій із підписаним
preview, строком 120 секунд і перевіркою користувача, дії та поточного інвентарю.
Заблоковані записи не доходять до preview. Докладні правила, JSON-результати
та межі ідемпотентності описані у [DASHBOARD.md](DASHBOARD.md).

`MODBUS_WRITES_ENABLED=False` у factory. Немає перемикача ввімкнення записів
у вебінтерфейсі чи з параметрів HTTP-запиту. За замовчуванням керування записом
повертає 403 до створення Modbus-клієнта. Низькорівневі функції також відмовляють
у записі за замовчуванням (`allow_write=False`). Тільки тести явно вмикають
прапорець і використовують in-memory mock; це не дозвіл на фізичні записи.

Команди перевіряються до будь-якого підключення:

- рівно одна дія з білого списку;
- 1–100 унікальних позитивних ID; невідомі ID відхиляють весь запит;
- для `limit` рівно одне ціле ASCII значення 1–100;
- немає fallback на 50%, обрізання діапазону або прийняття дробів;
- Operator не може обійти заборону видалення через `/control`.

За явного дозволу запису код перевіряє Modbus exception response, адресу та
значення відповіді FC06, а потім точне читання записаного регістра. Retries=0;
після втрати відповіді результат невідомий, автоматичного повторення немає.
Клієнт закривається у finally. Невдала команда дає danger-повідомлення.
Підтверджений запис регістра дає інформаційне повідомлення, яке прямо зазначає,
що фізичний стан інвертора не підтверджено. Повідомлень «інвертор запущено» або
«команда виконана» без фізичного підтвердження немає.

Карти регістрів 46 і 1000, значення 5/6 та масштаб 32767 успадковано й не
підтверджено для жодної фізичної моделі. Причину з регістра 47 більше не
використано як підтвердження успіху: перевіряється значення цільового регістра.
Перед майбутнім увімкненням реального керування потрібні модельний адаптер,
перевірена карта регістрів і окреме погодження конкретних фізичних операцій.
У TASK-03 моніторинг винесено з HTTP-запитів в окремий процес. Панель і
`GET /api/statuses` читають тільки SQLite, а ручні перевірки ставлять запит
на наступний цикл. Усі тести використовують mock, справжні socket і запуск
ping заблоковані фікстурою. Профіль Modbus-читання задається явно для кожного
інвертора; без нього Modbus не опитується. Спільні файлові блокування
захищають вебпроцес і монітор від одночасних підключень до одного IP/порту.
Правила станів, свіжості й підготовки додаткових таблиць: [MONITORING.md](MONITORING.md).

Паролі інверторів не підставляються в HTML. Порожнє поле редагування залишає
попереднє значення; нове непорожнє значення замінює його. Чинна схема інверторів
збережена; шифрування чи вилучення їхніх збережених паролів — окрема міграція.
Валідація нових/редагованих адрес приймає IP-літерали, відхиляє loopback,
unspecified і multicast. Allowlist конкретних інверторних підмереж ще не
впроваджено; адреси може задавати тільки Administrator.

## Ініціалізація схеми та облікових записів

На цьому етапі робоча БД не відкривалась і не мігрувалась. Модель інверторів
залишена сумісною; додано таблиці `user` та `login_throttle`. Код не виконує
`create_all()` під час звичайного імпорту чи запуску сервера.
TASK-03 додає ще чотири таблиці моніторингу, зберігаючи схеми та записи TASK-02;
їх також потрібно створити явно після резервного копіювання перед оновленням
вебпроцесу. Фоновий монітор відхиляє непідготовлену схему до мережевих перевірок.

Наведені команди призначені для окремого погодженого введення в експлуатацію
або нової ізольованої БД. Для наявної production-БД перед `init-db` необхідна
узгоджена резервна копія з урахуванням SQLite WAL; цей документ не є дозволом
на production-міграцію. `create_all()` тільки створює відсутні таблиці й не
замінює систему версійних міграцій майбутнього етапу.

Після безпечного надання INGECON_SECRET_KEY та INGECON_DATABASE_URI:

```bash
.venv/bin/python -m flask --app app init-db
.venv/bin/python -m flask --app app create-user admin --role Administrator
.venv/bin/python -m flask --app app create-user operator --role Operator
.venv/bin/python -m flask --app app create-user viewer --role Viewer
```

Пароль вводиться інтерактивно з підтвердженням. Не передавайте `--password`
із реальним паролем у shell history. Вебреєстрації та стандартних користувачів
немає. Подальше керування обліковими записами через вебпанель не входить до
TASK-02. Для виробничого запуску потрібні HTTPS і WSGI-сервер; Nginx та systemd
на цьому етапі не налаштовувались.

## Перевірки

```bash
.venv/bin/python -m pip install -r requirements-dev.lock
.venv/bin/python -m pytest -q
.venv/bin/python -m pip check
```

Тести блокують socket/DNS/subprocess.run, замінюють клієнт до імпорту застосунку
та використовують SQLite в пам’яті або окремі синтетичні tmp-файли.
CSRF не вимикається у тестах. Матриця ролей, відмова анонімам,
CSRF, session rotation, відкликання доступу, cookie, rate limiting, журнал без
секретів, приховані паролі, сувора валідація та результати команд перевіряються
автоматично. Попередні xfailed перетворено на звичайні тести.
