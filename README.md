# ingecon-control

INGECON SUN 100TL: [глобальна конфігурація Modbus, підтвердження команд і тестування регістрів](MODBUS.md).
Історичні й довільні записи заблоковані. Окремий дозвіл власника може ввімкнути
[тестове Start/Stop і ліміт для всіх зареєстрованих 100TL](CONTROL_ACTIVATION.md)
через спільний механізм вебпанелі та Telegram; без файла дозволу записи вимкнені.

Виявлення пристроїв вбудовано в **Додати інвертор**: автоматичний пошук за
погодженими приватними CIDR, L2 MAC-фільтр `00:25:CA:2C`, FC04-перевірка профілю,
прогрес/скасування та ручне додавання з портом і Unit ID. Доступ — Administrator.
Резервна копія перед трьома новими таблицями, окремий непривілейований worker
і межі ідентифікації: [DISCOVERY.md](DISCOVERY.md).
Production-сценарій із backup, перевірками, відкатом та release tag: [DISCOVERY_DEPLOY.md](DISCOVERY_DEPLOY.md). Production-схема цим комітом
автоматично не змінюється; службам потрібне окремо погоджене застосування коду.

У меню **Налаштування**: вкладка **Telegram** для всіх користувачів і
вкладка **Користувачі** для Administrator.
Кнопка **Додати користувача** доступна адміністратору в заголовку налаштувань з усіх вкладок.
Додавання, ролі та підтверджене видалення: [USER_MANAGEMENT.md](USER_MANAGEMENT.md).

На головній у таблиці **Пристрої** можна сортувати за назвою, групою, потужністю
та обмеженням: повторний клік заголовка змінює напрямок. На телефоні є окремі
списки колонки й напрямку. Додавання інверторів залишається у верхньому меню.

Опитування інверторів і оновлення статусів типово виконуються раз на **30 с**.
Адміністратор може задати інтервал від **1 с** на **30 хвилин**, після чого
автоматично відновиться 30 с. Реальне читання виконує єдиний монітор:
[MONITOR_POLLING.md](MONITOR_POLLING.md).

Демонстраційні режими видалено. Безпечне застосування очищення та перелік
збережених runtime-файлів: [DEPLOYMENT_CLEANUP.md](DEPLOYMENT_CLEANUP.md).
Автоматичні тести використовують mock; фізичне опитування цими змінами не запускається.

TASK-07: [внутрішній HTTP-портал, активація від root](HTTP_PORTAL.md).
Основний доступ — поточна DHCP IPv4-адреса сервера в локальній мережі.
Telegram — основний дистанційний канал, Tailscale — додатковий VPN-доступ.
Gunicorn тільки 127.0.0.1:5000, Nginx :80; LAN визначається динамічно без
фіксованої IP/підмережі. Веб і Telegram не залежать від наявності Tailscale.
Є fail-closed LAN-дозволи з timeout і окремий варіант Tailscale-only.
Вебпанель і бот працюють як systemd-служби; зміни коду застосовуються погодженим перезапуском.
Production-БД, `stewe`, постійний ключ і токен збережені; Modbus типово заблоковано.
Перевірка: **476 Python-тестів і 17 JS-тестів пройшли**; Telegram getMe успішний.

TASK-06: Telegram на aiogram 3.x із long polling, одноразовою прив’язкою
вебкористувачів, ролями, статусами з SQLite, сповіщеннями з дедуплікацією,
підтвердженнями й аудитом. Нинішній backend блокує фізичний запис незалежно
від старих per-device політик: [TELEGRAM_CONTROL.md](TELEGRAM_CONTROL.md).
Ручна підготовка з backup, токен, запуск і тести: [TELEGRAM.md](TELEGRAM.md).
Бот використовує наявну production-БД й токен; під час очищення не запускався новий polling.
Перевірка TASK-06: **408 Python-тестів (76 Telegram) та 17 JS-тестів пройшли**.

TASK-04: адаптивна панель, глобальні лічильники, незалежні проби,
автооновлення API, історія, серверне підтвердження, локальні ресурси та теми.
Інструкція й межі перевірок: [DASHBOARD.md](DASHBOARD.md).

TASK-03: додано окремий монітор, незалежні ICMP/TCP/Modbus-перевірки,
стани з порогами 3/2, heartbeat та API з кешу SQLite.
Архітектура, правила переходів, підготовка схеми, профілі читання і майбутній запуск:
[MONITORING.md](MONITORING.md). Монітор із реальними адресами не запускався.
TASK-02: збережено авторизацію, ролі, CSRF та захист команд.
Актуальні правила, налаштування секрету й створення користувачів: [SECURITY.md](SECURITY.md).
Modbus-записи заблоковані за замовчуванням. Робоча БД не мігрувалась.

Flask / SQLite застосунок керування інверторами. Аналіз і повний план модернізації:
[DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md).

## Основа етапу 1

Робоча гілка: `feature/modernization`. Runtime-файли вилучені з індексу Git,
але залишені на диску; Git-історія не переписувалась. Старий `venv/` не використовується.
Нові середовища, SQLite (включно з WAL/SHM/journal), журнали, кеші й типові секрети
виключено через `.gitignore`. Ігнорування не видаляє вже наявні дані з історії Git.
Потенційний витік секретів та потреба їх заміни потребують окремої оцінки.

Перевірене оточення: Debian amd64, Python 3.13.5, Flask 3.1.2,
Flask-SQLAlchemy 3.1.1, PyModbus 3.16.1, pytest 8.4.2.
`requirements.txt` і `requirements-dev.txt` описують прямі залежності;
`requirements.lock` і `requirements-dev.lock` фіксують також транзитивні залежності.
Для відтворення використовуйте lock-файли. Вони фіксують версії, але не хеші артефактів;
для завантаження потрібний доступ до PyPI. При оновленні залежностей потрібні повторні тести.

## Підготовка Python 3.13

Усі команди виконуйте в корені проєкту. Потрібні Python 3.13 і модуль `venv`.
Якщо Debian повідомляє про відсутність `ensurepip`, системний пакет
`python3.13-venv` встановлює адміністратор тільки після окремого погодження.
Не використовуйте `sudo pip` або `--break-system-packages`.

```bash
python3.13 -m venv .venv
.venv/bin/python -m pip install pip==25.2
.venv/bin/python -m pip install -r requirements-dev.lock
.venv/bin/python -m pip check
```

У середовищі реалізації `ensurepip` був відсутній, а sudo вимагав пароль.
Системних пакетів не встановлено. Локальне оточення підготовлено альтернативно
через офіційний pip zipapp, без зміни системного Python:

```bash
python3.13 -m venv --without-pip .venv
curl -fL https://bootstrap.pypa.io/pip/pip.pyz -o /tmp/ingecon-pip.pyz
python3.13 /tmp/ingecon-pip.pyz --python .venv install --no-cache-dir pip==25.2 -r requirements-dev.lock
```

Zipapp є засобом початкового встановлення; його URL не фіксує версію.
Версія встановленого pip зафіксована окремо. Стандартний шлях через `venv`
залишається рекомендованим для підготовленого Debian 13.
Для майбутнього runtime-оточення використовуйте `requirements.lock` без pytest.
Production-розгортання описано в [HTTP_PORTAL.md](HTTP_PORTAL.md); перед фізичними перевірками потрібна окрема перевірка модельних адаптерів.
Поточна телеметрія INGECON SUN 100TL (робочий стан, потужність, ліміт і причина)
та вибір профілю за моделлю описані в [MONITORING.md](MONITORING.md).
Адитивна міграція, backup і контрольований відкат: [TELEMETRY_DEPLOY.md](TELEMETRY_DEPLOY.md).
Dockerfile поки використовує Python 3.11; він не є способом відтворення цього етапу.

## Запуск автоматичних тестів

```bash
.venv/bin/python -m pytest -q
```

Окремі JS-тести TASK-04 (Node доступний у середовищі розробки;
для роботи вебпанелі Node не потрібний):

```bash
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
```

Тести мають власні підставні DOM/fetch і не звертаються до мережі.
Результат TASK-04: **272 Python-тест і 17 JS-тестів пройшли**; xfailed немає.

Не потрібно запускати `python app.py`, Flask-сервер, Modbus-сервер чи інвертори.
HTTP-маршрути pytest перевіряє внутрішнім Flask test client без сервера.
Додатковий offline-захист перевіряється командою `.venv/bin/python -m tests.device_guard_probe`.

Захист тестів:

- autouse-фікстура блокує створення socket, TCP connect/connect_ex, DNS та create_connection;
- справжній subprocess.run також заблоковано; ICMP перевіряється підставним runner;
- до імпорту застосунку Modbus-клієнт замінюється на `tests.fake_modbus.FakeModbusTcpClient`;
- mock читає й записує тільки Python-словник у пам’яті, не створюючи мережевих з’єднань;
- HTTP-тести використовують SQLite у пам’яті; тести монітора, доповнення схеми
  та перезапуску — окремі синтетичні файли у tmp_path. Робоча база не відкривається;
- поточний каталог перемикається на тимчасовий, а файлове налаштування журналу відключене;
- тестові адреси належать документаційному діапазону `192.0.2.0/24`.

Тести охоплюють CRUD, фільтри груп, відображення ліміту, вибір пристроїв,
пакетне видалення та перевірки доступності; start/stop і limit перевіряються
тільки на mock. Також перевірено сигнатури справжньої бібліотеки без створення клієнта.
Цей Python-захист призначений для поточного синхронного коду; нові транспорти
або бібліотеки мають отримати власну перевірку ізоляції до додавання тестів.

У TASK-01 було **26 passed, 2 xfailed**. Перед локальним комітом TASK-01
результат повторно підтверджено. Фінальний результат TASK-02: **150 passed**,
без xfailed і попереджень; `pip check` успішний. Обидва xfailed усунено;
CSRF перевіряється також у тестах. Додано перевірки ролей, входу, rate limiting,
приховування секретів і відмов команд. Наявний Query.get_or_404 у застосунку
замінено сучасним API.

У TASK-03 додано 67 тестів моніторингу: таймаути, недоступність, відновлення,
стани, heartbeat, застарілість, блокування між процесами та потоками, кешовані
вебстатуси, збереження даних TASK-02 й outbox для майбутнього Telegram-бота.
Окремий запуск:

```bash
.venv/bin/python -m pytest -q tests/test_monitoring.py
```

Перевірка TASK-03: **217 passed**, без xfailed і попереджень pytest.
`pip check`: залежності сумісні; `git diff --check`: успішно.
Реальне мережеве опитування та міграція робочої БД не виконувались.

## Зміни TASK-01 та TASK-02

`modbus_utils.py` адаптовано до сучасних імпорту, `device_id` та keyword-only `count`.
Регістри, значення команд і масштабування не змінено та не підтверджено для обладнання.
`app.py` отримав налаштування `INGECON_DATABASE_URI` до створення SQLAlchemy,
щоб тести могли використовувати БД у пам’яті. Типове значення URI збережено.
У TASK-02 додано application factory, моделі користувачів, авторизацію, CSRF,
структуровані результати та відхилення некоректних команд. Налаштування БД і ключа
описано в SECURITY.md. Не використовуйте поточний вебінтерфейс для реальних команд
до перевірки карт регістрів і окремого погодження.

Системні служби, firewall, SSH та мережеві налаштування на цьому етапі не змінюються.
