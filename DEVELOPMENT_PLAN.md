# Аналіз проєкту ingecon-control та план модернізації

Дата аналізу: 12 жовтня 2026 року.

## Висновок і межі аналізу

Проєкт є невеликим Flask-застосунком для обліку та групового керування інверторами через Modbus TCP. Його можна модернізувати на наявному стеку Python / Flask / SQLite, але поточний код не готовий до безпечної експлуатації: немає автентифікації, команди можуть помилково відображатися як успішні, а сумісність Modbus-коду порушена вже в наявному оточенні.

Прочитано `AGENTS.md`, `README.md`, усі Python-файли, `requirements.txt`, три HTML-шаблони, Docker-конфігурацію та `.gitignore`. Додатково перевірено метадані наявного `venv` і відповідний фрагмент бібліотеки PyModbus. Під час аналізу файли не змінювалися; пакети, застосунок і тести не запускалися; підключень до інверторів не було. Вміст бази даних і журналу не читався.

Цей документ зберігає результати статичного аналізу. Працездатність застосунку на Debian 13, коректність регістрів та виконання фізичних команд не перевірялися. Згадані версії залежностей відображають стан джерел на дату аналізу; перед реалізацією їх потрібно перевірити повторно.

## 1. Поточна архітектура

| Компонент | Реальний стан |
|---|---|
| `app.py` | Ініціалізація Flask, модель БД, маршрути, бізнес-логіка та запуск сервера в одному файлі |
| `models.py` | Порожній; модель `Inverter` визначена в `app.py` |
| `modbus_utils.py` | Синхронні TCP-підключення, читання та запис регістрів, файлове логування |
| SQLite | Одна модель: назва, група, адреса, логін і пароль інвертора |
| HTML | Jinja2, Bootstrap із CDN, невеликий JavaScript |
| `requirements.txt` | Flask, Flask-SQLAlchemy, PyModbus без фіксації версій |
| Розгортання | Docker із Python 3.11, запуск через вбудований Flask-сервер |
| `README.md` | Лише назва проєкту; інструкцій експлуатації немає |

Обробка головної сторінки:

```text
Браузер → Flask → SQLite: список інверторів
               → послідовні Modbus-підключення до кожного
               → формування HTML → браузер
```

Фонових процесів немає. Моніторинг відбувається тільки при відкритті сторінки, а керування — безпосередньо під час HTTP-запиту.

## 2. Наявна функціональність

Уже реалізовано:

- додавання, редагування та видалення інверторів;
- групування й фільтрацію;
- вибір кількох інверторів для спільної дії;
- перевірку TCP-з’єднання;
- команди запуску, зупинки, обмеження потужності й встановлення 100%;
- відображення розрахованого обмеження;
- завантаження журналу.

Відповідність вимогам `AGENTS.md`:

| Вимога | Стан |

| Адаптивна вебпанель | Частково: Bootstrap, адаптивна таблиця, але немає незалежного оновлення статусів |
| Моніторинг доступності | Частково: TCP-перевірка під час HTTP-запиту |
| Фоновий моніторинг | Відсутній |
| Telegram-бот | Відсутній |
| Start/stop | Є код запису, але немає належної перевірки результату й доступу |

Логін і пароль інвертора зберігаються, але не використовуються Modbus-кодом. Їхнє призначення треба уточнити перед перенесенням.

## 3. Проблеми безпеки

| Пріоритет | Знахідка | Наслідок |
|---|---|---|
| Критичний | Усі маршрути відкриті, включно з `/control` | Кожен, хто має мережевий доступ до застосунку, може надсилати команди й змінювати пристрої |
| Критичний | `debug=True`, прослуховування `0.0.0.0:5000` | Небезпечна конфігурація для експлуатації; фактичну зовнішню доступність не перевірено |
| Високий | Немає CSRF-захисту | Форми зміни даних і керування не захищені від підроблених запитів |
| Високий | `secret_key` записаний у коді | Ключ підпису сесій відомий і не має безпечного життєвого циклу |
| Високий | Паролі зберігаються відкритим текстом | Витік БД розкриває секрети |
| Високий | Пароль підставляється у HTML форми редагування | `type="password"` лише приховує його візуально; значення доступне у відповіді |
| Високий | Довільна адреса інвертора без серверної валідації | Застосунок можна використати для небажаних підключень до внутрішніх адрес на порт 502 |
| Високий | `/download-log` відкритий | Доступ до технічних відомостей без перевірки прав |
| Високий | База та журнал уже відстежуються Git | `.gitignore` не припиняє відстеження раніше доданих файлів |
| Середній | Немає обмеження частоти запитів і розміру пакетних операцій | Можливе перевантаження Flask і мережі інверторів |

Підтверджено відстеження `instance/database.db`, `modbus.log`, `venv` і скомпільованого Python-файлу. Наявність конкретних облікових даних у БД не перевірялася, але сама практика суперечить інструкціям проєкту.

Jinja-шаблони використовують звичайне екранування; явного `|safe` або очевидного SQL-конкатенування в прочитаному коді немає. Основні ризики тут — доступ до керування, секрети та перевірка команд.

## 4. Коректність і надійність Modbus

### 4.1. TCP-з’єднання не підтверджує справність Modbus чи роботу інвертора

`check_modbus_connection()` у `modbus_utils.py:12` виконує лише `connect()`. Порт може бути відкритий, але потрібний пристрій або регістр — недоступний. «Онлайн» також не означає «генерує».

### 4.2. Запис і відображення обмеження не узгоджені

`modbus_limit_power()` у `modbus_utils.py:48` записує відсоток у регістр `46` і читає причину з `47`. Натомість `read_command_status()` у `modbus_utils.py:85` використовує `1000–1001`, масштаб `32767`, а сторінка показує відсоток лише при команді `16`. Код не пояснює зв’язок між цими механізмами. Без документації конкретної моделі виправляти адреси чи масштабування небезпечно.

### 4.3. Start/stop не перевіряють відповідь запису

Результат `write_register()` і Modbus exception response ігноруються. Успішне TCP-підключення може завершитися відхиленою командою, але журнал повідомить про запуск або зупинку.

### 4.4. Вебінтерфейс повідомляє успіх незалежно від результату

Функції керування поглинають винятки й не повертають структурованого результату. Маршрут `/control` у `app.py:91` наприкінці завжди показує «команда виконана». Невідома дія також може дійти до цього повідомлення.

### 4.5. Некоректний відсоток перетворюється на реальну команду 50%

Замість відмови у виконанні використовується запасне значення. Для фізичного керування це неприйнятно.

### 4.6. Закриття клієнтів не гарантоване

Немає `finally`; у `read_command_status()` клієнт не закривається на деяких шляхах невдалого з’єднання або винятку.

### 4.7. Немає серіалізації команд для одного пристрою

Паралельні HTTP-запити можуть створювати конкурентні операції.

### 4.8. Параметри пристроїв зашиті в код

Порт `502`, ідентифікатор `1`, адреси та значення команд однакові для всіх інверторів. Виробник, модель, прошивка й версія карти регістрів не зберігаються.

Наявну логіку слід зберегти як матеріал для перевірки та тестових сценаріїв. Її працездатність на реальному обладнанні цей аналіз не підтверджує.

## 5. Debian 13 і сучасний PyModbus

### 5.1. Debian 13

Цільовий стек придатний для Debian 13 amd64. У дистрибутиві доступний Python 3.13; потрібне нове віртуальне оточення під цю версію, а не перенесення поточного `venv`. Його конфігурація вказує Python 3.11.2, старий шлях створення та наявність бінарних залежностей. Джерело: [пакет Python 3.13 у Debian](https://packages.debian.org/trixie/python3.13).

Потрібно перевірити весь набір залежностей на Python 3.13, включно з SQLAlchemy та бінарними wheel-пакетами. Декларація мінімальної версії Python у старих метаданих не є доказом такої сумісності. Залежності застосунку варто встановлювати в окремий `venv`, зберігаючи системний Python під керуванням Debian.

### 5.2. PyModbus

У наявному `venv` записано версію 2.5.3. Імпорт `pymodbus.client.sync` відповідає старому API, але виклики передають `slave=1`. У прочитаному локальному коді 2.5.3 ідентифікатор береться з `unit`, тому переданий `slave` не встановлює очікуваний Unit ID.

Для сучасної гілки потрібні такі зміни:

| Поточний код | Цільовий підхід |
|---|---|
| `from pymodbus.client.sync import ModbusTcpClient` | Імпорт із `pymodbus.client` |
| `slave=1` | `device_id=…` для версій 3.10+ |
| `read_holding_registers(1000, 2, ...)` | Іменований `count=2` |
| Необмежена залежність `pymodbus` | Конкретна перевірена версія |
| Перевірка тільки наявності `registers` | Перевірка помилки, довжини й значень відповіді |
| Результат запису ігнорується | Явний результат і подальше підтвердження стану |

Перехід `slave` → `device_id` відбувся у 3.10, а вимогу keyword-only параметрів запроваджено у 3.8. Джерело: [історія змін API PyModbus](https://pymodbus.readthedocs.io/en/latest/source/api_changes.html).

На дату аналізу PyPI показує стабільний PyModbus 3.16.1, Python ≥3.10 і підтримку Python 3.13. Це кандидат для перевірки, а не автоматично затверджена версія проєкту. Документація `/latest` уже позначена як 4.0 development, тому реалізацію треба звіряти з обраним стабільним релізом. Джерело: [PyModbus на PyPI](https://pypi.org/project/pymodbus/).

### 5.3. Flask і SQLite

Виявлено окрему помилку ініціалізації: код перевіряє `database.db` у поточному каталозі, хоча Flask-SQLAlchemy трактує `sqlite:///database.db` відносно `instance_path`. Перевірка існування й фактична БД можуть стосуватися різних файлів. `create_all()` також не замінює міграції та не виконується при звичайному WSGI-імпорті. Джерело: [конфігурація Flask-SQLAlchemy](https://flask-sqlalchemy.palletsprojects.com/en/stable/config/).

Вбудований сервер Flask не придатний для експлуатації навіть у локальній мережі; потрібен WSGI-сервер. Джерело: [офіційна документація Flask](https://flask.palletsprojects.com/en/stable/deploying/).

## 6. Проблеми вебпанелі та продуктивності

Головна сторінка в `app.py:30` послідовно робить щонайменше два підключення на інвертор: TCP-перевірку та читання статусу. Читання виконується навіть після негативної перевірки.

Час відповіді зростає приблизно як сума мережевих затримок усіх вибраних пристроїв; недоступні інвертори особливо погіршують ситуацію. Кілька користувачів повторюють однакове опитування й займають вебпроцеси.

Шаблони мають базову адаптивність, але:

- немає часу останнього успішного опитування й ознаки застарілих даних;
- немає розділення доступності, режиму роботи та результату команди;
- start/stop не потребують підтвердження;
- немає прогресу та результатів окремих пристроїв у груповій операції;
- ресурси залежать від зовнішніх CDN;
- повторюються сторінкова структура та підключення бібліотек;
- використано кілька наборів іконок;
- немає історії, ролей і налаштувань моніторингу.

## 7. Запропонована архітектура

Для Wyse 3040 рекомендовано залишити Flask, Jinja та SQLite, розділивши вебінтерфейс, моніторинг і Telegram на невеликі процеси:

```text
Браузер → Nginx → Gunicorn / Flask ───────┐
                                        │
                              SQLite: конфігурація,
                              статуси, команди, аудит
                                        │
Telegram → процес бота ──────────────────┤
                                        │
                         фоновий монітор / виконавець
                                        │
                             адаптер конкретної моделі
                                        │
                                     PyModbus
                                        │
                                    інвертор
```

- Вебпроцес читає збережені статуси та створює запити на команди.
- Монітор є єдиним власником Modbus-взаємодії, опитує пристрої та виконує дозволені команди.
- Бот використовує ті самі правила доступу й чергу команд.
- SQLite забезпечує короткі транзакції та невелику постійну чергу без Redis/Celery.
- systemd керує життєвим циклом процесів.
- Nginx обслуговує статичні файли й проксіює вебзапити.
- Fail2ban реагує на перевірені події невдалого входу.

У Flask доцільні application factory, окремі моделі, маршрути, сервіси авторизації/команд та каталог адаптерів. Docker для цільового розгортання не потрібний відповідно до `AGENTS.md`.

## 8. Поетапний план модернізації

### Етап 0 — зафіксувати вихідні дані та межі керування

- Скласти перелік моделей, прошивок, кількості інверторів, адрес, портів і Unit ID.
- Отримати офіційні карти регістрів для конкретних моделей.
- З’ясувати призначення полів логіна й пароля.
- Узгодити доступ користувачів, потрібні метрики та інтервали опитування.
- Визначити резервне копіювання, спосіб відновлення й часові межі застарілих команд.

Критерій завершення: для кожної моделі відомі дозволені операції; непідтверджені записи залишаються заблокованими.

### Етап 1 — відтворюване середовище та ізольовані тести

- Зафіксувати перевірені версії залежностей для Python 3.13.
- Створити нове оточення; не використовувати закомічений `venv`.
- Підготувати виключення для БД, журналів, секретів і кешів; припинити відстеження runtime-файлів із збереженням робочих даних.
- Окремо оцінити потребу очищення Git-історії та заміни потенційно розкритих секретів.
- Запровадити fake/mocked транспорт і режим, у якому записи фізично недоступні.
- Зафіксувати тестами поточні CRUD, групування й доступні дії.

Критерій завершення: проєкт відтворюється на тестовому Debian 13; тести не можуть звертатися до реальних інверторів.

### Етап 2 — закрити доступ і виправити небезпечну поведінку

- Додати користувачів, хешування паролів і ролі: спостерігач, оператор, адміністратор.
- Перевіряти права на сервері для кожного маршруту та пристрою.
- Додати CSRF, безпечні cookie, обмеження входів і серверну валідацію.
- Винести секрети з коду; припинити повертати паролі пристроїв у HTML.
- Обмежити адреси дозволеними інверторними мережами.
- Відхиляти невідомі дії, неправильні ID і некоректні відсотки без виконання команд.
- Захистити експорт журналів; замінити його контрольованою історією подій.

Критерій завершення: анонімний користувач і спостерігач не можуть керувати пристроями; помилковий запит не створює Modbus-запису.

### Етап 3 — розділити код і впорядкувати БД

- Перенести модель із `app.py` у модуль моделей.
- Додати сутності користувачів, профілів пристроїв, актуального стану, команд та аудиту.
- Зберігати виробника, модель, профіль регістрів, порт, Unit ID і доступні можливості.
- Запровадити явний шлях БД і версійні міграції.
- Перевірити міграцію та відновлення на копії даних.
- Для production перед міграцією зробити узгоджену резервну копію SQLite.

Критерій завершення: чинні записи та функції збережені; схема оновлюється контрольовано.

### Етап 4 — адаптери та сучасний PyModbus

- Оновити імпорт і сигнатури під обраний реліз.
- Відокремити транспорт від карти регістрів.
- Створити адаптер для підтвердженої моделі Ingeteam.
- Визначити інтерфейс читання стану та доступних операцій керування.
- Гарантувати закриття клієнтів, перевірку `isError()` і структури відповіді.
- Повертати структуровані результати замість приховування помилок.
- Перевірити адресацію, масштабування та порядок слів на mock-відповідях.

Критерій завершення: тести перевіряють точні адреси, Unit ID, значення та обробку помилок; невідомий профіль не допускає записів.

### Етап 5 — фоновий моніторинг

- Винести опитування з HTTP-запитів у окремий процес.
- Розділити TCP-доступність, успішний Modbus-відгук, режим роботи та свіжість даних.
- Зберігати `last_attempt`, `last_success`, тривалість і причину помилки.
- Додати backoff, невеликий jitter і пороги переходу offline/online.
- Почати з послідовного опитування або малої обмеженої паралельності.
- Серіалізувати операції для одного пристрою; не ділити клієнт між конкурентними викликами. PyModbus прямо вимагає такого контролю: [документація клієнта](https://pymodbus.readthedocs.io/en/latest/source/client.html).
- Додати heartbeat самого монітора.

Критерій завершення: недоступний інвертор не затримує вебпанель; зупинка монітора відображається як застарілі дані.

### Етап 6 — черга команд та аудит

- Вебпанель і бот створюють команди, виконавець обробляє їх.
- Передбачити стани `queued`, `running`, `succeeded`, `failed`, `unknown`, `expired`.
- Перевіряти права, профіль, дозвіл запису й актуальність команди перед виконанням.
- Додати підтвердження start/stop із конкретним списком пристроїв.
- Зберігати автора, джерело, цілі, час, параметри й результати кожного пристрою.
- Після втрати відповіді не повторювати запис автоматично: результат може бути невідомим.
- Не відтворювати небезпечні команди після перезапуску без перевірки.
- Розрізняти прийняття запису пристроєм і підтверджений фізичний стан.

Критерій завершення: немає неправдивих повідомлень про успіх; повторне надсилання форми не дублює виконання.

### Етап 7 — вебпанель

- Створити спільний `base.html`, локальні CSS/JS та один набір іконок.
- Зберегти CRUD, групи й пакетні операції.
- Додати легке періодичне оновлення статусів із БД без Modbus-запитів.
- Показувати свіжість даних, стан монітора, режим роботи та результати команд.
- Додати мобільне представлення, пошук, пагінацію, історію й підтвердження дій.
- Приховувати недоступні операції відповідно до можливостей адаптера та ролі.

Критерій завершення: панель працює без CDN, придатна для телефона й не збільшує частоту опитування інверторів.

### Етап 8 — Telegram-бот

- Використати long polling, щоб не потребувати публічного webhook.
- Почати зі статусу, списку груп і повідомлень offline/online.
- Зіставляти числовий Telegram user ID з активним локальним користувачем та його правами.
- Додати керування через спільну чергу з короткочасним одноразовим підтвердженням.
- Зберігати токен поза репозиторієм, не виводити його в журнал.
- Додати дедуплікацію updates, обмеження сповіщень і відновлення після втрати Інтернету.

Telegram підтримує long polling через `getUpdates`; polling і webhook взаємовиключні. Джерело: [Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

Критерій завершення: сторонній користувач не отримує дані й не створює команди; повторний update не дублює дію.

### Етап 9 — Nginx, systemd і Fail2ban

Спочатку підготувати конфігурації для перегляду, потім окремо погодити встановлення й активацію:

- Gunicorn із малою кількістю процесів, прив’язаний до localhost або Unix-сокета.
- Nginx зі статикою, TLS, лімітами запитів і коректною передачею адреси клієнта.
- Довіра до proxy-заголовків лише від визначеного проксі.
- Окремі systemd units для вебпроцесу, монітора та бота; непривілейований користувач, обмежені каталоги запису, контрольований restart.
- Структуровані події невдалого входу з перевіреною IP-адресою.
- Власний Fail2ban filter і jail для Flask-входу.
- Перевірка regex на позитивних, негативних і підроблених рядках журналу.

Стандартний `nginx-http-auth` орієнтований на помилки автентифікації Nginx; він не покриє автоматично форму входу Flask. Джерело: [офіційний фільтр Fail2ban](https://github.com/fail2ban/fail2ban/blob/master/config/filter.d/nginx-http-auth.conf).

Критерій завершення: перевірені адреси клієнтів і події входу; блокування не зачіпає всіх користувачів проксі. Активація ban actions потребує погодження, оскільки змінює правила мережевого доступу.

### Етап 10 — перевірка на Wyse та контрольоване введення

- Виміряти RAM, CPU, час відповіді, обсяг БД, журналів і записів на диск.
- Перевірити недоступність усіх пристроїв, втрату Інтернету, блокування SQLite, заповнення диска та перезапуски процесів.
- Перевірити резервне копіювання й відновлення.
- Провести тривалий прогін із mocks або ізольованим симулятором.
- Після окремого дозволу перевірити реальний моніторинг у режимі лише читання.
- Реальні записи дозволяти лише після перевірки документації та явного погодження конкретних операцій.

Критерій завершення: задокументовані результати, процедура відновлення та перевірені обмеження ресурсів.

## 9. Обмеження для Dell Wyse 3040

Цільове обладнання: Dell Wyse 3040, Debian 13 x86_64, Intel Atom x5-Z8350, 2 ГБ RAM, 8 ГБ eMMC.

Для 2 ГБ RAM і 8 ГБ eMMC головна економія досягається контрольованою частотою роботи та зберігання:

- мінімальна серверна інсталяція без desktop-середовища;
- невелика кількість вебпроцесів, один монітор і один бот;
- без Redis, Celery, окремого сервера БД та важкої SPA на початковому етапі;
- короткі SQLite-транзакції, індекси, `busy_timeout`; WAL перевірити під навантаженням;
- не записувати кожне успішне опитування в історію;
- зберігати переходи станів, команди й періодичні агрегати;
- обмежити журнали, строки зберігання та розмір експорту;
- резервні копії переносити на зовнішнє сховище;
- не знижувати надійність аудиту небезпечних команд заради економії записів.

Початковий інтервал опитування можна оцінювати в межах 30–60 секунд, але остаточне значення залежить від кількості пристроїв і їхніх вимог. За 30 секунд кожен інвертор дає 2880 циклів на добу — запис повної історії кожного циклу швидко накопичує зайві дані.

## 10. Порядок виконання та правила безпеки

Рекомендований порядок: спочатку ізольовані тести, захист доступу та виправлення результатів команд; далі адаптери й фоновий монітор; потім вебпанель, Telegram та системна інтеграція. Перевірка реального обладнання залишається окремим погодженим етапом.

Цей план не є дозволом на виконання фізичних команд або зміну системної конфігурації. Під час реалізації потрібно дотримуватися `AGENTS.md`:

- не надсилати реальні Modbus write-команди під час розробки й тестування;
- не запускати та не зупиняти фізичні інвертори без явного погодження;
- не вважати карти регістрів універсальними для різних моделей;
- використовувати mocks для всіх тестів керування;
- не відкривати застосунок публічно без автентифікації;
- не зберігати секрети у вихідному коді й не комітити облікові дані, БД або журнали;
- не виконувати руйнівні системні команди;
- погоджувати зміни firewall, SSH і мережевої конфігурації;
- робити резервну копію перед production-міграціями;
- запитувати дозвіл перед встановленням системних пакетів або зміною systemd-служб;
- зберігати наявну функціональність, робити невеликі перевірювані зміни й запускати відповідні тести після змін коду.
