# TASK-08: ізольований демонстраційний моніторинг

## Призначення та стан

Розділ **«Демо» → `/demo`** призначений тільки для Administrator.
Він показує віртуальний **DEMO-INVERTER-01**, реальні результати читання
локального Modbus TCP-симулятора, heartbeat, журнал та стан доставки `[DEMO]`.

Вебзапит не опитує інвертор. Зміна сценарію змінює лише налаштування
симулятора; показники й обладнання оновлюються тільки після FC03-опитування
окремим demo-worker. Використовуються спільні `NetworkProbes`, `MonitorWorker`,
`apply_observation`, `current_statuses` та механізм доставки `notification_batch`.

Підготовлено окрему runtime-БД `instance/monitor-demo/monitor.sqlite`.
Production-служби під час розробки **не перезапускалися**. Для завантаження
нових маршрутів у вже працюючий Gunicorn та demo-черги в уже працюючий бот
потрібен окремо погоджений перезапуск. До цього старі процеси виконують старий
код. Новий Telegram polling для TASK-08 запускати не потрібно.

## Ізоляція і безпека

- TASK-08 має власний каталог 0700 і SQLite 0600; дані не потрапляють у Git.
- `instance/production/ingecon.sqlite`, `instance/database.db`, `stewe`, ключі,
  токен та дані старого `instance/demo/` не перезаписуються й не мігруються.
- TASK-05 зберігає свій попередній повністю offline-режим; його облікові записи
  не отримують маршрутів керування TASK-08.
- Нові таблиці мають окрему SQLAlchemy metadata. Вони не додаються до
  production-схеми або до production-міграцій.
- Власна `demo_metadata` містить призначення `ingecon-monitor-demo-v1`.
  Чужа SQLite, symlink, hardlink, неправильний власник/права, production/demo
  каталог та неправильний marker відхиляються до DDL/робочого підключення.
- У demo-БД немає таблиці користувачів, паролів, ключів або токена. Для
  сповіщень зберігаються лише посилання на ID/версію чинного адміністратора.
- Звичайний production-монітор та звичайний Telegram CLI відхиляють demo-БД.
  Demo-worker приймає тільки тестовий endpoint і тестовий профіль.
- Симулятор прив’язаний тільки до **127.0.0.1:15020**, unit **1**. Немає
  параметра для прив’язки до LAN/WAN або адреси фізичного інвертора.
- Процеси simulator/monitor встановлюють незнімний Python audit guard:
  заборонені інші адреси, DNS, UDP/raw sockets і запуск дочірніх програм.
- Усі фізичні Modbus-записи залишаються заблокованими. Симулятор відхиляє
  write-функції; його стан змінюється через захищені форми та власну SQLite.
- SSH, firewall, Tailscale, Nginx і встановлені systemd-служби тут не змінюються.

Основні API, інвентар, історія та Telegram `/status`, `/inverters`, `/history`
залишаються production-даними. Віртуальний інвертор туди не додається.
`StateEvent`, heartbeat й статистика demo-monitor існують тільки у demo-файлі.
Номери demo-подій та реальних подій можуть збігатися — це різні БД й черги.

## Запуск без production-перезапусків

Виконуйте як власник проєкту `codex`, не як root. Підготовка ідемпотентна:

```bash
cd /opt/ingecon-control
.venv/bin/python demo_monitor.py init
```

Це створює тільки нове ізольоване сховище; сервер, worker, Telegram або
системні служби не запускаються. Наявна TASK-08 БД перевіряється й зберігається.
Секрети не генеруються і не змінюються, production-паролі не потрібні.

У **першому окремому терміналі** запустіть симулятор у foreground:

```bash
cd /opt/ingecon-control
.venv/bin/python demo_monitor.py simulator
```

У **другому терміналі** запустіть окремий demo-monitor:

```bash
cd /opt/ingecon-control
.venv/bin/python demo_monitor.py monitor --interval 5
```

Типовий інтервал TASK-08 — 5 секунд, допустимий — від 1 до 86400 секунд.
Це не змінює production-інтервал TASK-03, який за замовчуванням 30 секунд.
Другий worker для тієї самої БД відхиляється існуючим flock-механізмом.
Другий simulator не займає вже зайнятий порт. Не завершуйте невідомий процес,
якщо порт зайнятий; спочатку перевірте його походження.

Прочитати snapshot без мережевих перевірок:

```bash
.venv/bin/python demo_monitor.py status
```

Поки новий код вебпанелі не завантажено погодженим запуском/перезапуском,
перевіряйте CLI та автоматичні тести нижче. Сам TASK-08 не запускає ще один
Gunicorn або вебсервер і не займає production-порт 5000.

## Підключення до чинних systemd-процесів — після окремого дозволу

Шаблони `deploy/systemd/ingecon-web.service` і `ingecon-telegram.service`
дозволяють запис лише в додатковий `instance/monitor-demo` поряд з уже
наявними runtime-шляхами. Це потрібно через `ProtectSystem=strict`.
Приватні ключі/токен, користувач Linux, production-БД, мережеві bind та
обмеження пам’яті залишаються попередніми.

Спочатку створіть каталог командою `demo_monitor.py init` як codex.
Опціональний `ReadWritePaths=-...` для відсутнього каталогу не дає можливості
створити його після старту в read-only батьківському каталозі.

**Нижче команди для майбутнього окремо погодженого виконання під root.
Під час TASK-08 їх не виконували.** Перед заміною збережіть чинні unit-файли
в приватний root-backup. Після цього:

```bash
cd /opt/ingecon-control
task08_backup=$(mktemp -d /root/ingecon-task08-XXXXXXXX)
chmod 0700 "$task08_backup"
cp -a /etc/systemd/system/ingecon-web.service "$task08_backup/"
cp -a /etc/systemd/system/ingecon-telegram.service "$task08_backup/"
install -o root -g root -m 0644 deploy/systemd/ingecon-web.service /etc/systemd/system/ingecon-web.service
install -o root -g root -m 0644 deploy/systemd/ingecon-telegram.service /etc/systemd/system/ingecon-telegram.service
systemctl daemon-reload
systemctl restart ingecon-web.service
systemctl restart ingecon-telegram.service
systemctl is-active ingecon-web.service ingecon-telegram.service
```

Потрібні саме наявні служби. Не запускайте паралельно
`telegram_bot.py run` або другого бота з тим самим токеном. Systemd спочатку
зупиняє старий polling, потім запускає один новий; блокування за bot ID і БД
зберігаються. Нові simulator/monitor-служби не створюються й не вмикаються.
Якщо TASK-07 ще не активований, використовуйте погоджений порядок
[HTTP_PORTAL.md](HTTP_PORTAL.md) для первинної активації, а не наведений restart.

## Робота у вебпанелі

Після завантаження нового коду увійдіть існуючим Administrator і відкрийте
**«Демо»**. Нова форма й API мають ті самі авторизацію, CSRF, HTTPOnly,
SameSite та HTTP-cookie policy, що і решта вебпанелі.

Можна вибрати сценарій і навантаження 0–100% з точністю до 0.01%:

| Сценарій | Поведінка симулятора | Очікуваний виміряний результат |
|---|---|---|
| Нормальна робота | Читання доступне, обладнання Running | Unknown до другої успішної перевірки, потім Online |
| Аварія | Коректна Modbus-відповідь, Alarm, температура 85°C | Зв’язок Online; окрема аварія обладнання |
| Втрата зв’язку | TCP доступний, Modbus-відповідь затримується довше timeout | Degraded, Degraded, Offline |
| Відновлення зв’язку | Знову коректні відповіді, Running | Перша успішна перевірка Degraded, друга Online |
| Зупинка інвертора | Обладнання Stopped, потужність/струм 0 | Зв’язок залишається Online |

Для нормального/відновленого стану модель має номінальну потужність 5000 Вт;
навантаження 50% дає 2500 Вт, 80% — 4000 Вт. Це штучна навчальна модель,
а не характеристика Ingeteam або іншої фізичної моделі.

Кнопка повідомляє про збереження **налаштувань симулятора**, а не виконання
фізичної команди. Стан обладнання, температура та потужність не підміняються
вебформою. Якщо worker не працює, вони не оновлюються. При застарілому
heartbeat стан стає Unknown, поточні показники приховуються.

ICMP не застосовується до цього loopback-тесту. TCP й Modbus перевіряються
незалежно спільним механізмом. Падіння Modbus не приховується успішним TCP;
відсутність ICMP не заважає Online.

API `/api/demo/status` читає тільки demo-БД. Оновлення відбувається кожні
5 секунд без reload; після втрати HTTP-зв’язку або завислого запиту показники
не залишаються позначеними актуальними. Запит переривається через 8 секунд.
Після 401/403 автооновлення зупиняється. CSS/JS локальні, без CDN.

Журнал має час UTC та типи `scenario`, `load`, `equipment`, `availability`,
`notifications`; доступний фільтр. Повертаються останні 100 подій.
Сценарії/навантаження журналюються при зміні налаштувань, обладнання — при
зміні прочитаного стану, доступність — при фактичному переході монітора.
Кожен успішний цикл не створює нового запису історії.

## Telegram-сповіщення [DEMO]

Використовується **наявний бот**, його той самий токен і вже реалізований
механізм доставки. Demo-worker не звертається до Telegram і не читає токен.
Розширення існуючого notification loop ліниво відкриває demo-БД, якщо вона
підготовлена. Відсутність або помилка demo-БД не зупиняє production-бота.

Сповіщення за замовчуванням **вимкнені**, підписок немає. Для ввімкнення:

1. Майте чинну власну Telegram-прив’язку через звичайний розділ Telegram.
   TASK-08 не створює та не змінює її автоматично.
2. У розділі «Демо» поставте підтвердження тестових повідомлень.
3. Натисніть «Увімкнути на годину». Це дозволяє тільки власні `[DEMO]`-сповіщення,
   а не загальну розсилку. Довільний Telegram ID у формі не приймається як адресат.
4. Увімкніть аварію, дочекайтеся опитування й повідомлення Alarm.
5. Увімкніть втрату зв’язку, дочекайтеся трьох невдач і Offline.
6. Увімкніть відновлення, дочекайтеся двох успіхів і Online.
7. Перегляньте таблицю «Доставка [DEMO]», потім вимкніть тестові сповіщення.

Усі тестові повідомлення починаються **[DEMO]**, містять DEMO-INVERTER-01
та пояснення, що це не production-тривога. Відновлення після Alarm може
створити окрему подію обладнання поряд із відновленням доступності.
Події до ввімкнення не розсилаються; повторний незмінний цикл не дублює подію.

Окрема підписка має строк 1 годину. Перед доставкою повторно перевіряються
активність Administrator, session_version і чинна прив’язка з production **тільки
читанням**. Вихід із вебпанелі/зміна пароля/ролі/відкликання прив’язки роблять
demo-підписку недійсною. Відмова Telegram вимикає лише demo-сповіщення,
не production-налаштування. Дедуплікація має власний unique(event, telegram_id).

`sent` записується тільки після успішної відповіді Telegram. За неоднозначної
мережевої помилки — `unknown`, без автоматичного повтору; rate limit
планує обмежений повтор, до 5 спроб. Незавершена доставка після рестарту
також стає unknown. Недавні записи зберігаються; при працюючому боті раз на
годину очищуються demo-події старші доби, які виходять за останні 2000,
разом із відповідними demo-доставками. Production-історія цим не очищується.

Виконання автоматичних тестів не вмикає справжніх підписок і не надсилає
Telegram-повідомлень. Реальне ввімкнення робить тільки адміністратор у формі.

## Документована тестова карта регістрів

**Це власна карта TASK-08, НЕ карта Ingeteam.** Не переносіть її в адаптер
реального інвертора. PDU-адресація від нуля, unit 1, TCP 127.0.0.1:15020.
Монітор читає FC03, address=0, count=8, `device_id=1` (PyModbus 3.16.1).

| PDU-адреса | Значення | Масштаб / пояснення |
|---:|---|---|
| 0 | `0xD008` | Ідентифікатор тестового протоколу |
| 1 | `1` | Версія карти |
| 2 | Потужність | uint16, Вт, 0–5000 |
| 3 | Напруга | uint16 / 10, В; тестово 230.0 |
| 4 | Струм | uint16 / 10, А; потужність / 230 |
| 5 | Частота | uint16 / 100, Гц; тестово 50.00 |
| 6 | Температура | uint16 / 10, °C; аварія 85.0 |
| 7 | Стан обладнання | 0 Running, 1 Alarm, 2 Stopped |

Невірна magic/version, довжина чи equipment code відхиляються адаптером.
Симулятор перевіряє MBAP protocol/length, unit і діапазон читання. Усі інші
function codes, включно з 05/06/15/16/22/23, повертають Illegal Function.
Жоден register write не змінює налаштування симулятора.

## Зупинка

Вимкніть сповіщення в «Демо». Натисніть **Ctrl+C** в терміналі demo-monitor,
потім **Ctrl+C** у терміналі simulator. SIGTERM також підтримується.
Worker записує stopped heartbeat тільки до своєї demo-БД. Production-бот,
вебпанель та фізичні пристрої не зупиняються. Demo-файл збережено для журналу;
повторний init його не очищує. Не використовуйте `pkill`, не видаляйте lock-файли.

## Перевірки

Усі звичайні pytest-тести блокують реальні socket/DNS/subprocess. Для
Modbus використовується wire-aware mock, для Telegram — FakeTelegramSession.
Автоматичні тести також перенаправляють demo discovery бота/вебу в tmp_path,
щоб не відкривати навіть підготовлений оператором runtime-файл TASK-08.

```bash
.venv/bin/python -m pytest -q
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
node tests/js/monitor_demo.test.cjs
.venv/bin/python -m pip check --disable-pip-version-check --no-cache-dir
git diff --check
```

Окремий явний smoke-тест справжнього TCP лише по loopback:

```bash
.venv/bin/python -m tests.demo_monitor_smoke
```

Він створює тимчасову SQLite й власний дочірній simulator, чекає підтвердження
готовності саме цього процесу, встановлює loopback-only audit guard, читає
FC03 справжнім PyModbus та перевіряє сценарії. Власний дочірній процес
завершується після тесту. Записів Modbus, ICMP, віддалених адрес, токена,
Telegram API та production-процесів у ньому немає. Тест не входить до pytest,
бо навмисно використовує справжній TCP; якщо 15020 зайнятий, він припиняється
до опитування невідомого endpoint і нікого не завершує.

Щоб згодом підключити фізичні інвертори, використовуйте перевірені адаптери
реального обладнання та окремо налаштований production-монітор TASK-03.
Спільна state machine вже перевірена; тестову карту і loopback-профіль
переносити в production не потрібно.

## Результат реалізації

Перевірено повний pytest-набір, локальні JS-тести й окремий реальний FC03
loopback smoke. Покрито ролі/CSRF, сценарії та гістерезис, протокол і відхилення
write-функцій, stale heartbeat, ізоляцію схем/файлів, відсутність доступу
TASK-05 до TASK-08, безпечну навігацію старого worker, окреме opt-in, дедуплікацію,
відкликання ролей/прив’язок, неоднозначні помилки Telegram й роботу основного
бота при недоступності demo-файлу. Нових пакетів не встановлено.

Результати: повний pytest-набір — **546 passed**; модуль TASK-08 в остаточній
редакції з додатковою перевіркою нормалізації `..` у шляхах — **71 passed**.
**23 JS-тести пройшли** (17 наявних і 6 нових). Реальний guarded loopback FC03
smoke, `pip check`, `systemd-analyze verify` шаблонів та `git diff --check`
успішні. Жоден тест не надсилав реальних Telegram-повідомлень.

Чинний Gunicorn під час завершення відповів `/login` → 200. Nginx, вебслужба,
Telegram-служба й Tailscale активні за systemd; вони не перезапускалися цими
діями. Тимчасовий smoke simulator завершено, постійних demo-процесів немає.

Production-БД штатно використовується працюючою вебпанеллю й ботом, тому
runtime-таблиці входів/Telegram можуть відрізнятися від старої копії TASK-07.
Вони не відкотилися. Повний запис stewe незмінний відносно перевіреної копії.
Додатково зроблено свіжий узгоджений SQLite backup без DDL і зміни секретів:

```text
instance/production/backups/pre-http-portal-20261018T101416.598077Z.sqlite
```

Новий каталог TASK-08 підготовлено з вимкненими сповіщеннями й Unknown до
першого реального опитування симулятора. Розділ з’явиться у працюючому вебі
лише після окремо погодженого завантаження нового коду; до цього навігація
старого застосунку продовжує працювати. Цей документ не є твердженням, що
production-worker або production-polling уже виконують код TASK-08.
