# INGECON SUN 100TL: конфігурація й підготовка Modbus-команд

## Поточний режим

Фізичний Modbus-запис заблоковано на backend у `modbus_safety.py` перед
створенням клієнта й перед FC06. Цю заборону не знімають роль Administrator,
`allow_write=True`, `MODBUS_WRITES_ENABLED`, змінні середовища, стара Telegram
політика або тестова панель. Звичайний `portal.py` додатково блокує транспорт.
Історичні команди мають статус **непідтверджені**.

На сторінці огляду для Administrator/Operator є посилання
**Керування Modbus · попередній перегляд**. На сторінці керування:
вибір зареєстрованого інвертора, кнопки **Увімкнути**, **Вимкнути**,
**Застосувати ліміт**, **Максимум · 100 %**. Підтвердження показує точні
ID/назву/IP, TCP-порт, Unit ID, функцію, адресу й значення.
Після підтвердження запис не відбувається; результат прямо повідомляє блокування.
Наявні CRUD, групові операції, авторизація й Telegram збережені.

## Одна глобальна конфігурація

Administrator відкриває **Налаштування → Modbus** (`/settings/modbus`).
Конфігурація спільна для всіх інверторів, спільного виконавця команд і бота.
Історичні початкові значення:

| Призначення | Простір | Адреса протоколу | Значення |
|---|---|---|---|
| Увімкнути | Holding, FC06 | 1000 | 6 |
| Вимкнути | Holding, FC06 | 1000 | 5 |
| Обмеження | Holding, FC06 | 46 | ціле 1–100 |
| Читання обмеження | Holding, FC03 | 1001 | сире слово |
| Читання причини | Holding, FC03 | 47 | сире слово |

Транспортні значення: TCP 502, Unit ID 1, timeout 2 секунди.
Редагуються адреси, значення Start/Stop, порт (1–65535), Unit ID (1–247)
та таймаут (1–10 с). Адреси/слова — цілі 0–65535. Межі відсотка 1–100 незмінні.
Дроби, булеві значення замість чисел, дублікати та невідомі поля відхиляються.
Значення є нульовими адресами протоколу; `1000` не перетворюється на `999`.
Ці команди не оголошуються офіційно підтвердженими навіть після збереження.

Файл за замовчуванням — `/opt/ingecon-control/instance/production/modbus.json`.
Інший спільний шлях можна явно задати через `INGECON_MODBUS_CONFIG_FILE`
однаково для вебу/бота та інших споживачів. Якщо файлу немає, використовуються
вбудовані історичні значення; імпорт/GET не створює його. Перше збереження
через UI створює приватний файл 0600, власник — користувач служби.
Секретів у ньому немає; runtime-файл не комітиться. Пошкоджений, сторонній
чи незахищений файл не замінюється мовчки типовими значеннями.

Збереження серіалізується файловим lock і виконується через атомарний rename.
Відбиток конфігурації запобігає перезапису чужого свіжішого редагування.
Зміна ревізії анулює старі підтвердження. `modbus_config` у наявному
`command_audit` містить автора, час, попередні/нові значення й результат.
Спочатку фіксується `pending`, після файлової операції — `saved`/`rejected`.
При збою остаточного audit commit UI не повідомляє успіх: потрібно перевірити
файл і журнал. Стан `pending` може означати незавершене журналювання.
Нових SQLite-таблиць немає, міграція або `init-db` не потрібні.

## Панель тестування регістрів

Administrator: **Налаштування → Modbus → Панель тестування регістрів**
(`/settings/modbus/registers`). Operator може лише підготувати історичні
команди, Viewer не має доступу до цих операцій.

Поля: зареєстрований інвертор, IP, порт, Unit ID, функція, нульова адреса,
кількість регістрів та значення через кому. IP має точно відповідати
вибраному запису; hostname, loopback, multicast та сторонні адреси відхиляються.
Паролі інверторів у HTML або аудит не передаються.

Підтримано FC03/FC04 для читання та FC06/FC16 для **підготовки заблокованого
запису**. Інші функції, зокрема змішані читання/запис FC23, відхиляються.
FC03/04: 1–125 слів і порожнє поле значення; FC06: одне слово;
FC16: 1–123 слів, довжина списку має збігатися. Переповнення діапазону адрес
відхиляється. Панель не викликає жодного write-методу навіть тоді, коли інший
тестовий або майбутній командний шлях дозволений окремо.

Кожна дія потребує CSRF й окремого одноразового підтвердження на 120 секунд,
прив’язаного до користувача, цілі, параметрів і відбитка конфігурації.
`CommandAudit` атомарно переводиться `preview` → `processing` перед дією.
Повторне підтвердження не виконує операцію повторно. Результати: `blocked`,
`read`, `busy`, `unconfirmed`. При втраті фінального DB commit можливий
невідомий результат; автоматичного повторення немає. Фізичного запису це
не допускає: write-функції тестової панелі завжди завершуються `blocked`.

Фізичне **читання** також вимкнено за замовчуванням. Його подальший явний
серверний дозвіл: `INGECON_REGISTER_READS_ENABLED=true` для вебпроцесу.
Цей параметр не редагується через HTTP і не дозволяє записів. Без нього
навіть підтверджений FC03/04 не створює Modbus-клієнта. Автоопитування
при відкритті сторінки немає. Реальне читання потребуватиме окремого дозволу
на зміну конфігурації/перезапуск вебслужби; у цій реалізації цього не робили.
Спільний endpoint-lock за IP/портом виключає паралельні Modbus-операції.

## Окрема довідкова карта Input Registers

Джерело: документ виробника **AAA0030IMB02_Q**, 03.05.2024, §7.1, стор.25–27,
3Play 100TL/160TL, ABS1004; доступна [публічна копія документа Ingeteam](https://de.scribd.com/document/1045182807/AAA0030IMB02-Q).
Це не карта SUN STORAGE або іншого сімейства. Сумісність конкретної прошивки
потрібно перевірити окремо. Каталог та одиниці збережено в `input_registers.py`
і показано у вкладці Modbus; до редагованих Holding-команд вони не належать.
`30001 + offset` — довідкова Modicon-адреса; читання використовує **FC04**.

Профіль `ingecon_100tl_input` читає тільки два блоки: 20–35 і 52–54.
Він не вмикається автоматично й потребує явного `configure-monitor`
із `--read-address 20 --read-count 16 --profile ingecon_100tl_input`
та перевіреними портом/Unit ID для зареєстрованого інвертора.
Тільки явний новий профіль використовує FC04; старі профілі не мігруються.
Поточне обмеження для цього профілю береться з Input 52 як 0–100 %.
`read_legacy_limits()` окремо читає сирі HR1001 та HR47 із глобальної карти,
без перенесення одиниць або масштабів з Input Registers.

Статистику виробітку, енергетичні лічильники, аналітичні графіки й
моніторинг окремих стрінгів не додано. Історія станів працює за чинними правилами.

## Майбутня активація

Потрібні окремо підтверджена сумісність моделі/прошивки, дозволи для конкретних
команд і прив’язка дозволу до відбитка глобальної карти. Зміна карти має
відкликати дозвіл. `modbus_safety.py` — спільна точка такого майбутнього
розгортання; зараз її неможливо розблокувати JSON-полем, env або вебформою.
Старі per-device карти Telegram не є альтернативною картою виконання.
Поточне [Telegram-керування](TELEGRAM_CONTROL.md) лишається заблокованим.

## Перевірки та застосування

```bash
.venv/bin/python -m pytest -q
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
.venv/bin/python -m tests.device_guard_probe
```

Позитивні write-тести явно знімають міжблокування тільки в mock-фікстурі;
IP-сокети та DNS заблоковані, реальні клієнти замінено на Python-словники.
Інші тести доводять чинність backend-блокування без такого перевизначення.
Для aiogram/asyncio потрібен локальний AF_UNIX socketpair; це не IP-мережа.

У production нічого не активовано: SQLite, stewe, Telegram-прив’язки, токен,
SECRET_KEY та runtime-файли не редагувалися. Нові конфігурації створюються лише
за подальшої явної дії адміністратора. Systemd/Nginx/firewall/SSH/Tailscale
не змінено, служби не перезапускались. Застосування нового коду потребує
погодженого перезапуску відповідних наявних Python-процесів; не запускайте
додатковий Telegram polling і не застосовуйте застарілі інструкції розблокування.
