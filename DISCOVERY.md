# Виявлення та додавання INGECON SUN 100TL

Функціональність знаходиться на **«Додати інвертор» (`/add`)**. Окремої сторінки пошуку немає. Доступ до додавання, підмереж, результатів та API має тільки Administrator. За замовчуванням відкрито «Автоматичний пошук»; «Додати вручну» доступне незалежно від worker і підготовки нових таблиць.

## Як працює пошук

1. Вебпанель читає локальні IPv4-інтерфейси та маршрути через `ip -json`. Це локальний netlink-запит, без ping, DNS або підключень до інверторів. Правила визначення фізичних активних Ethernet/Wi-Fi сегментів повторно використовують `deploy.http_guard.discover`; VPN, Tailscale, loopback, PPP, віртуальні та неоднозначні інтерфейси не стають дозволеними LAN.
2. Виявлений сегмент **не є автоматичним дозволом сканувати**. Адміністратор погоджує конкретний CIDR на цій самій сторінці. Можна додати інші приватні мережі, вибрати одну, кілька або всі погоджені.
3. Приймаються тільки RFC1918 (`10/8`, `172.16/12`, `192.168/16`), у межах яких окремий дозволений діапазон повинен бути `/22`–`/30`. Максимум 32 погоджені діапазони й 1024 унікальні адреси на запуск. Понад 254 адреси потребують окремої позначки підтвердження. Великі локальні сегменти, наприклад `/16`, треба погоджувати меншими частинами; довільний великий діапазон не сканується.
4. Для локального L2-сегмента звичайне коротке TCP-підключення до 502 також дозволяє ядру оновити ARP/neighbor cache. Потім читається MAC через `ip neigh`. Сирі ARP-сокети, `arp-scan`, `CAP_NET_RAW`, root і додаткові пакети не потрібні. Відомий інший MAC відсіюється; MAC `00:25:CA:2C:*:*` допускає FC04. Якщо MAC недоступна, але TCP відкритий, результат позначається «Можливий інвертор», а FC04 у локальному режимі не виконується — MAC-фільтр не обходиться.
5. Для маршрутизованої мережі MAC цілі не очікується: MAC шлюзу не вважається MAC інвертора. Потрібен явний приватний маршрут у main routing table, який покриває весь погоджений CIDR, через локальний приватний шлюз на підтвердженому фізичному інтерфейсі. **Одного default route недостатньо.** Маршрути не додаються й не змінюються. Якщо доказу маршрутизації немає, використайте ручне додавання або окремо погодьте мережеві роботи з адміністратором.
6. Після TCP перевіряються **тільки FC04 Input Registers 20–35 і 52–54** з наявної карти [MODBUS.md](MODBUS.md). Використовується вибраний Unit ID (1–247), порт 502, timeout TCP 0,4 с, кожного Modbus-запиту 1 с, без автоматичних повторів. Unit ID не перебираються.
7. Валідність довжини й слів перевіряє спільний `register_tools.read_registers`; евристика профілю додатково відхиляє повністю нульові/FFFF блоки, невідомий стан FFFF, неправдоподібні AC-напруги, частоту та ліміт. Це перевірка правдоподібності, **не унікальний ідентифікатор виробника чи моделі**. Зупинений інвертор може мати нульові напругу/частоту.
8. Доступний порт 502 без FC04 — лише «Можливий інвертор». Навіть успішний профіль має позначку «Відповідає очікуваному профілю», без гарантії моделі. Відповідність MAC також не гарантує модель. Недоступний TCP показується для знайденого локального MAC потрібного префікса; відсутні адреси й сторонні MAC не захаращують результати.

Перед **кожним** TCP/FC04-з'єднанням повторно перевіряються CIDR, локальні адреси, фізичний інтерфейс, маршрут та джерело. Сканування власних адрес сервера, через VPN-інтерфейси, публічних, CGNAT, link-local, multicast і службових діапазонів заборонене. Зміна маршруту під час пошуку завершує його помилкою. Це зменшує ризик роботи зі старим DHCP-сегментом; конфігурація не містить фіксованої IP сервера або фіксованої LAN-підмережі. Маршрути приватної мережі за стороннім VPN-шлюзом неможливо відрізнити від звичайної маршрутизації лише на сервері: адміністратор має погоджувати CIDR тільки своєї дозволеної мережі.

## Черга, ресурси та історія

Gunicorn тільки ставить завдання в SQLite й читає результати. Власне сканування виконує окремий непривілейований `discovery_worker.py`; процес моніторингу та Telegram-бот не використовуються для сканування. Запуск worker сам по собі не сканує: потрібне завдання адміністратора.

Одночасно виконується один пошук, до чотирьох потоків. Адреси обробляються пакетами по чотири; після пакета фіксуються прогрес, результати й heartbeat. Усі Modbus-читання використовують спільні блокування адреси/порту, як вебпанель і монітор. SQLite-з'єднання не утримуються під час мережевої перевірки. Worker блокує свій повторний запуск через advisory lock. Паралельні натискання «Почати» серіалізуються між процесами.

«Скасувати» одразу знімає завдання в черзі або зупиняє активне після поточного обмеженого пакета. Відкликання CIDR, деактивація адміністратора, зміна його ролі або версії сесії теж зупиняють подальші пакети. Незавершений пошук після аварійного завершення worker при наступному запуску позначається помилкою й автоматично повторно не запускається. Черга без worker не виконується; через 30 секунд UI попереджає про застарілий heartbeat/очікування worker.

API оновлюється приблизно кожні 2,5 с, показує стан, кількість адрес, результати та втрату зв'язку/сесії. Попередні 20 пошуків доступні на цій самій сторінці. Загальний ліміт — 200 збережених пошуків: після цього нові запуски блокуються до окремо погодженої архівації. Автоматичного видалення історії немає, обсяг записів результатів обмежений приблизно 200 × 1024 рядками. Збережені результати можна переглядати після завершення; статус дубліката перевіряється за поточним обліком при читанні API. Погодження/видалення CIDR, постановка, скасування й завершення пошуку пишуться в наявний `CommandAudit`; старт/завершення також журналюються logger `ingecon.discovery`. Немає запису кожного невдалого IP в окремий audit. Реальні StateEvent, Telegram-черга і статистика моніторингу не змінюються.

## Додавання та транспорт

Результат містить IP, MAC (якщо доступна), CIDR, TCP/Modbus і висновок профілю, «Вже доданий»/«Новий». «Додати» **не створює запис**, а відкриває ручну форму з IP, портом і Unit ID. Назву та групу задає адміністратор. Потрібне явне підтвердження збереження без перевірки доступності; додавання не виконує мережевих запитів.

Дублікати перевіряються за **IP + порт + Unit ID** при додаванні й редагуванні під спільним блокуванням обліку. Існуючі інвертори без `MonitorConfig` використовують глобальні транспортні значення; старі записи не переписуються. Новий запис використовує наявний `MonitorConfig`, без зміни схеми `inverter`. Один IP може обслуговувати різні Unit ID. Порт 1–65535, Unit ID 1–247; неоднозначні й нечислові значення відхиляються. Паролі не повертаються в HTML.

Профіль читання не вмикається автоматично навіть для кандидата: після перевірки обладнання адміністратор вибирає підтверджену модель, як описано у [MONITORING.md](MONITORING.md). Для INGECON SUN 100TL це автоматично обирає спільний профіль FC04 без окремих налаштувань для IP. Глобальна карта непідтверджених команд залишається спільною й не змінюється при додаванні. Фізичний Modbus-запис заблокований незмінним backend-запобіжником; пошук взагалі не має write-шляху. `INGECON_REGISTER_READS_ENABLED` стосується ручної тестової панелі у вебпроцесі; для окремого worker дозволом є погоджений CIDR та явно поставлене адміністратором завдання.

## Безпечне застосування на сервері

Ці кроки **не виконуються автоматично**. Production-БД, служби, секрети, firewall, маршрути, SSH і Tailscale під час розробки не змінюються. Нові таблиці необов'язкові для завантаження порталу: до підготовки схеми працює ручне додавання, API пошуку повертає 503. Зміни Python-коду почнуть діяти тільки після окремо погодженого перезапуску вебслужби.

Від користувача `codex`, без root, підготувати **резервну копію й лише три нові таблиці**:

```bash
cd /opt/ingecon-control
.venv/bin/python -m discovery_schema \
  --database /opt/ingecon-control/instance/production/ingecon.sqlite \
  --backup-dir /opt/ingecon-control/instance/production/backups
```

`discovery_schema` спочатку виконує online SQLite backup у новий файл 0600, `quick_check`, fsync, потім `CREATE TABLE IF NOT EXISTS` тільки для `discovery_subnet`, `discovery_scan`, `discovery_result`. Наявні таблиці й рядки не змінюються; backup не перезаписується. Повторний запуск створює ще одну копію. Не використовуйте загальний `init-db` як міграцію. За вимогою цей крок має виконати користувач після перегляду змін, а не агент на production.

Після **окремого підтвердження** власника сервера, від root, тільки вебпанель:

```bash
systemctl restart ingecon-web.service
systemctl is-active ingecon-web.service
```

Telegram, монітор, Nginx і мережеві служби перезапускати не потрібно. Нові unit-файли й overrides не встановлюються. У наявній вебслужбі залишається `User=codex`.

В іншому терміналі **від codex**, у foreground:

```bash
cd /opt/ingecon-control
.venv/bin/python -m discovery_worker \
  --database /opt/ingecon-control/instance/production/ingecon.sqlite --run
```

Зупинка worker — Ctrl+C; поточний пакет завершиться й активний пошук стане скасованим. Не запускайте його від root (CLI це забороняє). Для разового оброблення одного вже поставленого завдання додайте `--once`; якщо черга порожня, процес одразу завершиться. Постійний автозапуск потребує окремого погодження systemd та не налаштовується цим завданням. Не запускайте discovery worker через Flask/Gunicorn hooks.

Після запуску: Administrator → Додати інвертор → погодити свій CIDR → вибрати діапазони → Почати → перевірити прогрес/скасування → Додати кандидат → переглянути форму → підтвердити збереження. Це **реальний read-only пошук**, тому запускати його слід лише в дозволеній мережі, коли готові перевіряти обладнання. У межах розробки реальні сканування не виконуються.

## Автоматизована перевірка

```bash
.venv/bin/python -m pytest -q tests/test_discovery.py tests/test_web.py tests/test_security.py
.venv/bin/python -m pytest -q
node tests/js/discovery.test.cjs
```

Тести підміняють netlink inventory/route, TCP, MAC та Telegram/Modbus; загальна fixture забороняє реальні sockets, DNS і subprocess. Перевіряються L2/MAC, маршрутизовані мережі без MAC, недоступність/таймаути/хибний профіль, дублікати, ручне підтверджене додавання, права/CSRF, заборонені CIDR/VPN/зміни маршруту, черга/скасування/відновлення після аварії та адитивна схема на синтетичній БД. Тести керування й читання використовують виключно mocks; production SQLite не відкривається.

## Production-розгортання з перевірками та відкатом

Після дозволу власника сервера використовуйте [DISCOVERY_DEPLOY.md](DISCOVERY_DEPLOY.md):
перевірений commit на GitHub, приватний source/config/SQLite snapshot,
`deploy/activate_discovery.sh` із автоматичним відкатом, непривілейовані
systemd worker і монітор, live HTTP/Telegram перевірки та тег після успіху.
Цей узгоджений сценарій замінює ручний foreground-запуск вище, коли потрібна
постійна production-служба. Він не ставить завдань пошуку й не змінює мережу.
У вебслужбі потрібен AF_NETLINK для читання інтерфейсів через `ip`.
