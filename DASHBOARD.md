# TASK-04: адаптивна вебпанель

## Інтерфейс

Flask/Jinja2 використовує спільний `base.html` для огляду, входу, CRUD,
історії, підтвердження та помилок. Чотири локальні ресурси `static/panel.css`,
`theme.js`, `panel.js`, `dashboard.js` займають приблизно 32 КБ без стиснення.
Немає CDN, зовнішніх fonts, frontend-фреймворків, npm-залежностей чи build-кроку.

Головна сторінка показує загальну кількість інверторів і Online, Offline,
Degraded, Unknown **для всього парку**. Комбіновані пошук за назвою/IP/групою,
фільтр групи та ефективного стану обмежують список, але не загальну статистику.
Рядки показують незалежні ICMP/TCP/Modbus, київський час перевірки й останнього
успіху, затримку Modbus, ліміт за наявності, застарілість та пояснення.

Заголовки **Назва / IP**, **Група**, **Активна потужність** і **Обмеження (%)**
сортують рядки: перший клік — за зростанням, повторний — за спаданням.
Назва сортується за назвою пристрою, українські літери порівнюються без урахування
регістру; числа в назвах мають природний порядок (2 перед 10). Потужність і ліміт
порівнюються як числа, не як форматований текст. Нуль є значенням; відсутні або
застарілі показники завжди йдуть останніми. Для однакових значень порядок визначає ID.
На телефоні, де заголовки приховані, доступні списки **Сортувати за** і **Порядок**.
Напрямок позначено стрілкою й `aria-sort`, кнопки працюють із клавіатури.

Сортування зберігається під час автооновлення й фільтрації в поточній вкладці,
враховує нові значення потужності та не змінює вибір інверторів за ID.
Перезавантаження сторінки повертає початковий порядок додавання. Сортування локальне:
без додаткових запитів, Modbus-операцій, POST-команд або зміни API/БД.
Кнопки мають `type="button"`, тому не відправляють форму керування.
Дубльовану кнопку додавання з блоку **Пристрої** прибрано; **Додати інвертор**
залишається у верхньому меню адміністратора.

До 760 px таблиці перетворюються на картки з підписаними полями; до 1100 px
навігація переноситься в окремий рядок. Є видимий клавіатурний фокус, посилання
на основний вміст, підписи checkbox/dialog, повідомлення `role=alert`, результати
з `aria-live`. Колір проб доповнюється ✓ / × / —. Темна/світла тема враховує
системну перевагу й зберігає ручний вибір у localStorage браузера. Якщо storage
недоступний, перемикання продовжує працювати. Секрети й статуси там не зберігаються.

## Автооновлення і свіжість

Видима панель читає `GET /api/statuses` типово кожні 30 секунд із timeout 8 секунд,
без паралельних запитів. При прихованій вкладці нові запити призупиняються;
повернення запускає оновлення. При 401/403 цикл зупиняється з повідомленням
про необхідність входу. Сервер перевіряє актуальність сесії та ролі як у TASK-02.

Дані інверторів API й HTML читають **лише з SQLite**. Типовий інтервал монітора —
30 секунд, TTL — 90 секунд, пороги 3/2 збережені. Адміністратор може встановити
спільний тимчасовий інтервал від 1 секунди на 30 хвилин; цей самий інтервал
використовує вебпанель. Налаштування читається з окремого приватного файла.
За повільного циклу фактичний період і TTL враховують час читання.
Правила, перевірки та застосування: [MONITOR_POLLING.md](MONITOR_POLLING.md).
При помилці API залишається останній отриманий знімок з повідомленням.
Після відновлення повідомлення прибирається. Під час втрати API незалежний
клієнтський tick також переводить прострочені результати й heartbeat у Unknown.
Час сервера `generated_at` плюс монотонний elapsed time виключає залежність
від часового поясу/годинника браузера. Застарілі проби та ліміт приховуються;
історичний час не вважається свіжою перевіркою.
Якщо ще перший API-запит завершується невдачею, початкові HTML-лічильники
й індикатори консервативно показуються як Unknown до успішного оновлення.

API зберігає поля `monitor` і `inverters` TASK-03 та додає `counts` для всього
парку, `groups`, `generated_at` у секундах UTC і локалізований `reason_text`
у рядках. Параметри `q`, `group`, `state` фільтрують список; неправильні значення
дають 400. Неавторизований запит повертає JSON `error` і 401. Паролі інверторів,
хеші користувачів і секрети сесій у HTML/API не повертаються.

## Ролі й підтвердження команд

Administrator керує CRUD, видаленням і завантаженням журналу; Operator може
обирати пристрої й планувати перевірки; Viewer переглядає панель, API та історію.
Перевірка прав виконується сервером незалежно від кнопок. POST-форми та JS
мають CSRF. Створення/редагування не підключається до пристрою, а порожній
пароль під час редагування зберігає попередній.

Групові дії підтримують до 100 видимих інверторів. При фільтрації чи видаленні
приховані ID прибираються з вибору. Ручна перевірка лише ставить запит на
наступний цикл монітора. Modbus-записи заблоковані сервером і кнопками;
перемикача ввімкнення TASK-04 не додає. Регістри й Modbus-функції не змінені.

Видалення та потенційні start/stop/limit проходять два кроки:

1. POST із CSRF і валідною командою перевіряє роль та дозвіл і створює preview.
   Небезпечна дія не виконується. Заблокований запис одразу повертає 403.
2. Після перевірки назв, IP, дії та відсотка користувач надсилає окреме
   підтвердження. Сервер перевіряє підписаний токен із TTL 120 секунд, прив'язаний
   до користувача, версії сесії, ролі, дії/значення та ID/назви/групи/IP кожного
   пристрою. Зміна цих даних вимагає нового підтвердження.

JS показує dialog; без JS/підтримки dialog працює серверна сторінка.
Це стосується також прямого POST `/delete/<id>`. Скасування не виконує дію,
подвійний клік у dialog не надсилає дві команди. Після втрати зв'язку автоматичного
повтору немає; повідомляється невідомий результат. За недоступності API JS
блокує початок команди та скасовує старе підтвердження.

При `Accept: application/json` успішний запит повертає `results`: окремі `id`,
`name`, `outcome`, `message` за кожним інвертором. Outcome: `queued`, `deleted`,
`register_confirmed`, `unconfirmed`. Підтвердження регістра не стверджує фізичний
запуск; текст TASK-02 збережено. Звичайні форми отримують HTML-сторінку
результатів із HTTP 200; до підтвердження теж повертається HTTP 200 з preview.
Звіт великих груп не зберігається в session cookie. CRUD створення/редагування
та одиночний запит перевірки зберігають свої звичайні redirect-відповіді.
POST має timeout 12 секунд; після нього результат серверної операції може
лишитися невідомим, тому клієнт не повторює команду.

Preview не є чергою команд чи серверною гарантією exactly-once: коректний
HTTP-запит може повторно використати токен у межах TTL. До майбутнього дозволу
фізичних записів потрібні ідемпотентність, черга/аудит, модельні адаптери та
погодження обладнання відповідно до плану. У тестах записи дозволені лише mock.

## Історія

`GET /history` доступний усім ролям та читає наявні `state_event` TASK-03.
Показує київський час, збережені назву/ID інвертора, попередній/новий стан і причину.
Історія видалених пристроїв лишається доступною. Це історія переходів станів,
а не повний журнал команд чи фізичної генерації.

Фільтри: назва (`q`), ID (`inverter_id`), новий стан (`state`), початкова й
кінцева дата (`since`, `until`) за `Europe/Kyiv`; кінцева дата включає весь місцевий день (23, 24 або 25 годин).
SQL-wildcards пошуку трактуються буквально. Невалідні дати, ID, стани та
сторінки відхиляються з 400. Показується до 50 найновіших за ID подій;
запит бере 51 рядок для визначення наступної сторінки без повного COUNT.
Пагінація зберігає фільтри. Історична група не реконструюється з поточного
інвентарю: у подіях TASK-03 її немає. Наявні дані не очищаються й не мігруються.

## Захист і тести

CSP дозволяє script/style/connect тільки з того самого origin. Inline-скрипти,
стилі та обробники вилучено. Статичні ресурси публічні й не містять інвентарю
або секретів. Jinja екранує HTML, JS використовує DOM/textContent без innerHTML.
Вебсписок/API працює з невеликим парком у пам'яті; історія має пагінацію.
Реальне навантаження на Wyse 3040 не вимірювалось.

Команди з кореня проєкту:

```bash
.venv/bin/python -m pytest -q
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
.venv/bin/python -m pip --disable-pip-version-check --no-cache-dir check
git diff --check
```

Результат: **272 passed** у Python та **17 passed** у JavaScript, без xfailed.
`pip check` і `git diff --check` успішні. Python-тести блокують socket/DNS/subprocess,
використовують fake Modbus та синтетичні БД. Позитивні тести небезпечних дій
проходять двокроковий HTTP-сценарій; тести відмов лишаються прямими.
Перевірено ролі, CSRF, API, фільтри, пагінацію, HTML, відсутність CDN/inline,
підробку/застаріння/зміну підтвердження та результати за інверторами.

Node потрібний лише для тестів, без npm-пакетів; production-панель його не
використовує. JS-тести підставляють DOM/fetch, не запускають сервер або браузер
і не створюють мережевих підключень. Вони перевіряють оновлення, недоступність
API, відновлення, свіжість, скасування, подвійний клік та теми. Реальний рендеринг
у браузерах/на телефонах не перевірявся; потрібен ручний огляд на ізольованому стенді.

Перевірки сортування й кнопки створення користувача:
155 Python-тестів і 73 JavaScript-тести пройшли; перевірки виконані в ізольованій копії.

```bash
.venv/bin/python -m pytest -q tests/test_dashboard.py tests/test_settings.py tests/test_users.py tests/test_telemetry.py tests/test_limit_reasons.py
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
node tests/js/discovery.test.cjs
```

Нові елементи шаблонів потребують погодженого перезапуску лише `ingecon-web`
та оновлення вкладки Ctrl+Shift+R. Підготовка backup і повернення попередніх
файлів представлення — за [LIMIT_REASONS.md](LIMIT_REASONS.md#оновлення-production).
Перезапуск монітора, Telegram або discovery worker не потрібний; автоматично
служби не перезапускаються, користувачі в production не створюються.

Нові таблиці/міграції не потрібні. Підготовка попередньої схеми для майбутнього
введення в експлуатацію: [SECURITY.md](SECURITY.md), [MONITORING.md](MONITORING.md).
Робоча БД, журнал, Modbus-логіка, systemd, firewall, SSH і Nginx не змінені;
реальний монітор не запускався, push не виконувався.

## Пошук на сторінці додавання

`/add` тепер має два режими: типовий автоматичний і ручний (`?mode=manual`).
Погодження CIDR, результати попередніх пошуків і прогрес показуються на тій
самій сторінці, лише Administrator. Вибір кандидата заповнює ручну форму
IP/порт/Unit ID, але не зберігає інвертор без підтвердження. Недоступність
не забороняє ручне додавання. Збережено групи й поля облікових даних.

Виявлення відокремлено від монітора, виконується одним обмеженим worker;
сторінка тільки опитує захищений API результатів без мережевого сканування.
Підготовка нових таблиць, запуск, мережеві обмеження й додаткові тести описані
в [DISCOVERY.md](DISCOVERY.md). Уточнення щодо схеми вище для початкового
TASK-04 не стосується цього нового модуля. JS-перевірки нового інтерфейсу:

```bash
node tests/js/discovery.test.cjs
```

## Час у вебпанелі й Telegram

Час перевірки, heartbeat, історії, пошуку, контролера та повідомлень Telegram
відображається за `Europe/Kyiv` із позначкою «Київ». Літній і зимовий час
враховуються автоматично. Часовий пояс браузера та системний часовий пояс
сервера не впливають на відображення. Фільтри дат історії задають київські дні.
Unix timestamps у SQLite/API, таймаути, інтервали опитування та UTC-імена
резервних копій і релізів збережені. Міграція БД не потрібна. Python використовує
системну базу часових поясів Debian (`zoneinfo`, `Europe/Kyiv`).

Після перевірки й публікації commit для повної активації потрібне перезавантаження
процесів вебпанелі та єдиного Telegram-бота. Перед цим збережіть поточний SHA,
перевірену SQLite backup і snapshot конфігурації. Від root:

```sh
cd /opt/ingecon-control
systemctl restart ingecon-web.service ingecon-telegram.service
systemctl is-active ingecon-web.service ingecon-telegram.service
```

Монітор, discovery worker, Nginx, контролер і системний час змін не потребують.
Старі вебпроцеси до перезапуску зберігають позначку UTC для серверних дат;
оновлений JavaScript форматує дані API за Києвом і оновлює відповідні позначки.
Після перезапуску перевірте головну, історію та «Статус» у Telegram.
Не застосовуйте команди керування для перевірки часових поясів.
