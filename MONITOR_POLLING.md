# Тимчасовий інтервал реального опитування

На головній у блоці **Оновлення даних інверторів** адміністратор задає цілий
інтервал **1–86400 секунд** і натискає **Застосувати на 30 хв**. Змінюється
read-only опитування всіх зареєстрованих інверторів. Числові показники надалі
надходять із фізичних FC04-читань монітора до SQLite, звідти — у вебпанель.
Вебобробник не виконує ICMP, TCP або Modbus-запитів.

За замовчуванням інтервал **30 секунд**. Сервер задає строк дії **1800 секунд**;
кожна наступна явна зміна запускає нові 30 хвилин. Кнопка **Повернути 30 с**
скасовує зміну раніше. GET сторінки/API, відкрита чи закрита вкладка, оновлення
сторінки та перезапуск монітора не продовжують строк. Інтервал понад 30 хвилин
може закінчитися до наступного запланованого циклу: тоді діятимуть звичайні 30 с.

Змінює налаштування лише **Administrator**, через POST із CSRF. Operator і Viewer
бачать бажаний інтервал, залишок часу та період, який повідомляє монітор.
Результат збереження параметра не є підтвердженням отримання нової телеметрії:
перевіряйте час останньої перевірки та heartbeat. За неактивного монітора дані
залишаються Unknown/застарілими. Журнал вебслужби фіксує ID адміністратора,
інтервал і строк завершення без секретів.

## Монітор і навантаження

Єдиний процес монітора перечитує налаштування щонайпізніше після поточної
мережевої операції/циклу; у паузах перевіряє його щосекунди. Окремий процес або
паралельні Modbus-операції не запускаються. Час читання віднімається від періоду:
цикл 0,4 с за інтервалу 1 с залишає паузу 0,6 с. Якщо цикл довший за інтервал,
наступний починається після завершення й паузи 1 с, без накопичення пропусків.

Інтервал 1 с є запитаним періодом. Тривалість опитування всього парку, таймаути,
зайняті endpoint-lock і продуктивність Wyse 3040 визначають досяжну частоту.
Heartbeat показує досяжний період; вік актуальності та розрив гістерезису
враховують тривалість циклу, щоб не створювати хибну застарілість.
Пороги двох успішних/трьох невдалих перевірок, профілі, регістри, значення
команд, конфігурація дозволів керування та Telegram-прив’язки не змінюються.
Історія й далі пишеться при зміні стану; поточні показники — короткими пакетними
транзакціями після читання, без утримання SQLite-транзакції під час мережевої операції.

## Спільна конфігурація без міграції

`monitor_schedule.py` використовує приватний JSON користувача служби:

```text
/opt/ingecon-control/instance/production/monitor-schedule.json
```

Він створюється лише при першому явному збереженні з панелі. Права **0600**,
атомарна заміна, спільний lock; symlink, чужий власник, відкриті права й некоректний
вміст не приймаються. Строк перевіряється за часом сервера. Прострочення не
перезаписує файл щосекунди: обидва процеси просто використовують 30 с.
Відсутній файл означає штатний інтервал; пошкоджений — безпечний fallback 30 с.
UI відображає помилку, запис поверх пошкодженого/небезпечного файла заборонений.

Для окремих середовищ підтримано `INGECON_MONITOR_SCHEDULE_FILE`: шлях має бути
однаковим у вебі й моніторі. Тестові фікстури задають власний tmp_path. У штатних
unit-файлах обидві служби вже мають доступ до `instance/production`, тому зміни
systemd-конфігурації не потрібні. SQLite, користувачі, секрети й списки інверторів
не мігруються й не перезаписуються.

API `/api/statuses` додатково повертає `polling` із бажаним інтервалом і
`expires_at`. Наявні поля збережені. Браузер рахує строк за часом API та
монотонним таймером, повертає 30 с також при втраті API й після повернення
прихованої вкладки. Відкликана сесія не запускає нових опитувань API.

## Тести

```bash
.venv/bin/python -m pytest -q tests/test_monitor_schedule.py tests/test_monitoring.py tests/test_dashboard.py tests/test_telemetry.py tests/test_limit_reasons.py tests/test_settings.py
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
node tests/js/discovery.test.cjs
```

Фізична мережа заблокована фікстурами. Перевірено реальний worker і два FC04-блоки
через in-memory Modbus mock, зміну показників у SQLite, 1 с, строк 30 хв,
перехід до 30 с без вебсесії, довгі інтервали/цикли, ролі, CSRF, валідацію,
пошкоджені файли, автооновлення й помилки API. Modbus write у цих перевірках немає.
Результат: **207 Python-тестів та 79 JavaScript-тестів пройшли**. Python повідомив
одне наявне попередження `multiprocessing/fork` у тесті міжпроцесного lock;
помилок і xfailed немає.

## Погоджене застосування та відкат

Спочатку опублікувати commit у GitHub/main. Перед змінами checkout зберегти
перевірений SQLite backup і source/config snapshot за чинною процедурою;
якщо `monitor-schedule.json` уже існує, додати його до приватної копії конфігурації,
зберігши первинний строк дії. Не виводити секретів. Міграцій і нових пакетів немає.

Після окремого погодження активації потрібні лише:

```bash
sudo systemctl restart ingecon-monitor.service ingecon-web.service
sudo systemctl is-active ingecon-monitor.service ingecon-web.service
```

Після Ctrl+Shift+R адміністратор бачить новий блок. Спочатку перевірити інтервал
30 с, heartbeat і час останнього читання. Тимчасовий інтервал перевіряє власник
через панель; під час розробки його в production не застосовують. Не надсилати
start/stop/limit. Telegram, discovery, Nginx, firewall, SSH, Tailscale не змінюються.
Ця підготовка не перезапускає production-служби автоматично.

Для відкату повернути попередній source snapshot, зокрема `monitor.py`, `app.py`,
шаблон і JS, та погоджено перезапустити ті самі дві служби. Попередня версія
ігнорує новий JSON і повертається до штатного `--interval 30`. Runtime-файл
зберегти для діагностики, SQLite поверх нових даних не відновлювати. Після
успішної активації й перевірки створити та опублікувати production release tag.
