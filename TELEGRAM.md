# TASK-06: Telegram integration

Окремий процес на **aiogram 3.31.0**, Python 3.13 і long polling. Вебпанель,
монітор і бот використовують одну явно вибрану SQLite-БД. Бот не запускається
при імпорті, разом із Flask чи автоматично як системна служба. Webhook, Redis,
Docker, додатковий HTTP-порт і важкий frontend не потрібні.

Статуси надходять лише з SQLite через той самий `current_statuses`, що й у
вебпанелі: heartbeat, застарілі дані, незалежні ICMP/TCP/Modbus-результати й
ефективний Unknown зберігають правила TASK-03. Бот не опитує інвертори.
Без окремого дозволу фізичні команди заблоковані. Власник дозволив тестове
керування всіма зареєстрованими 100TL через фіксований командний профіль;
активація та межі сумісності: [CONTROL_ACTIVATION.md](CONTROL_ACTIVATION.md).

## Що реалізовано

| Команда | Поведінка |
|---|---|
| `/start` | Прив’язка через `/start КОД` або інтерактивне меню |
| `/status` | Запит нового опитування монітором, кількість, доступність, генерація у кВт і фактичний час вимірів |
| `/inverters` | Інвертори з адресами, кешованими станами й потужністю, сторінки по 8 |
| `/groups` | Віртуальна група «Усі» та збережені групи; перегляд/дозволене керування |
| `/history` | Останні 8 переходів станів із київським часом (`Europe/Kyiv`) та ID події |
| `/help` | Інструкція, прив’язка й обмеження; доступна без прив’язки |
| `/notifications` | Увімкнення, стани Online/Offline/Degraded та фільтр групи |
| `/control` | Вибір інвертора/групи для двоетапного Start/Stop за явною політикою пристроїв |
| `/limit ID ВІДСОТОК` | Підготовка ліміту 1–100 % з окремим підтвердженням для дозволеного 100TL |
| `/cancel` | Скасувати поточне ручне введення ліміту |

Меню використовує inline-кнопки. Viewer бачить статуси, історію, інвертори,
групи та власні сповіщення. Administrator і Operator також можуть підготувати
й підтвердити Start/Stop та ліміт. Без нового дозволу старе міжблокування
залишає результат «заблоковано». Ролі перевіряються на сервері, включно з
підробленими callback data. Невідомий користувач не отримує інвентар.

## Ручне введення ліміту потужності

Сумарний автоматичний ліміт у **кВт** для всього парку — окремий режим:
[POWER_BUDGET.md](POWER_BUDGET.md), меню **Керування → Загальний ліміт, кВт**,
команди `/power` і `/poweroff`. Він потребує окремого контролера та активації;
наведені нижче ручні відсотки залишаються окремою дією.

Кнопки 25/50/75/100 % замінені на **Ввести ліміт** та **Максимум 100%**
у картках інвертора, збереженої групи й віртуальної групи «Усі».
Для Administrator/Operator із чинним дозволом керування:

1. Відкрийте `/control` або `/groups` і виберіть ціль.
2. Натисніть **Ввести ліміт**, надішліть ціле число **1–100**, наприклад `37`
   або `37%`. Бот пропонує відповідь на своє повідомлення. Дробові значення,
   0, значення понад 100 та довільний текст відхиляються без виконання команди.
3. Перевірте відсоток, повний список пристроїв, адреси, порти та Unit ID
   у попередньому перегляді. Лише кнопка **Підтвердити** запускає наявний
   спільний механізм команди. **Скасувати** відхиляє готове підтвердження.

**Максимум 100%** одразу готує таке саме одноразове підтвердження для 100 %;
саме натискання цієї кнопки нічого не записує в інвертор.
Команда `/limit ID ВІДСОТОК` збережена для ручного введення ID.

Запит введення діє **5 хвилин**, готове підтвердження — **120 секунд**.
`/cancel` скасовує введення. Відкриття іншої цілі/списку/меню також його скасовує.
Нова команда або новий запит замінюють попередні незавершені запити користувача.
Відповідь на старе повідомлення не застосовується до нової цілі; введення
непідв’язаного користувача відхиляється. Звичайне текстове повідомлення без
Telegram reply обробляється лише в контексті поточного запиту введення.

Контекст зберігається в наявній `telegram_command` у SQLite та переживає
перезапуск бота. Нових таблиць, міграцій, залежностей або налаштувань не потрібно.
Перед прийняттям числа та перед виконанням повторно перевіряються користувач,
роль, чинний дозвіл, конфігурація, точний склад групи й параметри пристроїв.
Зміни анулюють запит; нові пристрої не додаються непомітно. Аудит містить
Telegram ID, користувача, список цілей і результат. Введення відсотка саме
по собі не виконує Modbus-операцій. Карта регістрів і фізичний механізм команд
не змінені, спільна межа 100 пристроїв збережена.

Перевірки виконуються лише з mock Telegram/Modbus і синтетичною SQLite:

```bash
.venv/bin/python -m pytest -q tests/test_telegram_limits.py tests/test_telegram.py tests/test_telegram_controls.py tests/test_telegram_fleet.py tests/test_telegram_status_groups.py tests/test_telegram_sessions.py tests/test_inverter_controls.py
```

Результат цієї перевірки: **276 тестів пройшли**, зокрема 62 нові перевірки
ручного введення, максимуму, скасування, прав, перезапуску, строку дії,
зміни цілей/конфігурації та групового ліміту для 25 пристроїв.

Після публікації у `origin/main` та перевіреного SQLite backup/source snapshot
для активації потрібен перезапуск **лише наявного** екземпляра бота:

```bash
sudo systemctl restart ingecon-telegram.service
sudo systemctl is-active ingecon-telegram.service
```

Потім відкрийте `/start` або `/control`: раніше надіслані Telegram-повідомлення
зберігають старі кнопки. Другий polling не запускайте. Вебслужбу перезапускати
не потрібно. Для відкату поверніть `telegram_ui.py`, `telegram_store.py` та
`telegram_bot.py` із попереднього source snapshot і погоджено перезапустіть
той самий бот. Скасовані запити не відновлюйте зі старої БД: достатньо створити
нове підтвердження. Токен, прив’язки й production-дані залишаються на місці.

## Генерація, група «Усі» та короткі результати

`/status` і кнопка **Статус** показують сумарну поточну активну потужність у кВт,
наприклад `Поточна генерація: 63,98 кВт`, час формування відповіді та час вимірів
монітора (Київ, `Europe/Kyiv`, із літнім/зимовим часом). Кнопка **Статус** і `/status` тепер запитують новий знімок через
наявні `MonitorConfig.requested_at` у SQLite. Інвертори опитує тільки фоновий
монітор; сам Telegram-бот не відкриває ICMP/TCP/Modbus-з'єднань.
Нуль показується як `0,00 кВт`, підписаний від’ємний потік не обрізається.
Відсутні або застарілі значення не перетворюються на нуль: за часткових даних
сума має позначку `часткові дані M/N`, без актуальних показників — `—`.
Статистика виробітку, kWh та аналітика не додаються.

Спочатку бот відповідає **Оновлюю показники N інверторів…**, потім до 15 секунд
чекає, доки для всього зареєстрованого складу буде новий `checked_at` не раніше
моменту натискання. Монітор перевіряє запити раз на секунду під час очікування
планового циклу й починає наступне опитування достроково. Повторні запити
використовують ті самі поля, не створюють чергу паралельних опитувань; примусові
цикли починаються не частіше ніж раз на 5 секунд. Налаштований коротший інтервал
(наприклад 1 с) збережено. Усі Unit ID одного endpoint-а та записи/читання
залишаються захищені наявними locks. Реєстрів запису ця дія не використовує.

Після підтвердження нового опитування показується **Поточна генерація** з часом
реальних вимірів. Час формування відповіді підписаний окремо. Таймаут, часткове
оновлення або зупинений монітор не маскуються новим часом: бот явно повідомляє,
що оновлення не підтверджено, і використовує підпис **Остання відома генерація**.
Помилка FC04 очищає показник потужності відповідного пристрою звичайною логікою
монітора; старе значення не підставляється як нове, недоступність не стає нулем.
Зміна IP/порту/Unit ID/складу та відкликання прив'язки повторно перевіряються
під час очікування. Нових таблиць, міграцій або залежностей немає.

Перевірка лише через mock Telegram/FC04 і синтетичну SQLite:

```bash
.venv/bin/python -m pytest -q tests/test_status_refresh.py tests/test_telegram.py tests/test_telegram_status_groups.py tests/test_monitor_schedule.py tests/test_monitoring.py
```

Після публікації, перевіреного backup і погодженого застосування необхідно
оновити **обидва** наявні процеси, щоб монітор умів обробляти достроковий запит:

```bash
sudo systemctl restart ingecon-monitor.service ingecon-telegram.service
sudo systemctl is-active ingecon-monitor.service ingecon-telegram.service
```

Другий монітор або polling-бот не запускаються. Якщо ще очікується первинна
активація автоматичного ліміту, створіть свіжий manifest для нового SHA через
`deploy.power_release prepare` і використовуйте підготовлений root-сценарій
із [POWER_BUDGET.md](POWER_BUDGET.md); старий manifest іншого коміту буде відхилено.

У **Групи** першою є **Усі**. Це віртуальна група всього зареєстрованого обладнання,
без перейменування або перенесення інверторів у SQLite. Нове обладнання входить
до неї автоматично. Список має сторінки по 8 пристроїв, стан і потужність кожного;
усі сторінки доступні й для великих парків. Якщо є реальна група з назвою «Усі»,
вона показується як `Усі (збережена група)` й лишається окремою ціллю.
Фільтр сповіщень «Усі групи» й надалі охоплює всі групи.

Окреме обмеження Telegram у 10 пристроїв **знято**. Звичайні групи й «Усі»
використовують наявну спільну межу `commands.MAX_CONTROL_TARGETS = 100`, як вебпанель.
Команди на парк із 20+, 25 або до 100 інверторів проходять одним підтвердженням
повного списку ID, включно з іншими сторінками. Додавання, видалення чи редагування
цілі анулює його. Більші пакети не обрізаються мовчки: потрібно вибрати меншу групу.
Ролі, чинні дозволи й двоетапне підтвердження збережені. Перевірка дозволів
виконується для всіх цілей до першого запису, далі пристрої обробляються послідовно.
Нова група не розблоковує невідомі моделі, регістри або пристрої.

Офіційний [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage) обмежує
текст повідомлення 4096 символами. Довгі списки й результати діляться без втрати
символів, із запасом до 3500 UTF-16 одиниць на частину; emoji не розрізаються
посеред кодової точки. Між частинами є пауза 1 с. Кнопки підтвердження/скасування
надсилаються лише в останній частині, після всього списку. Якщо попередня частина
не надіслалася, кнопки не надсилаються. Невідомі мережеві помилки не запускають
повторення фізичної команди. Аудит зберігає повний список і результати кожного пристрою.

Успішний результат у боті тепер короткий: `Записи команд підтверджено.` і результат
кожного інвертора. Фразу про непідтверджений фізичний стан прибрано з Telegram.
Це підтвердження запису, а не повідомлення «інвертор увімкнено» без телеметрії.
Помилки, часткові та невідомі результати залишені. Повні повідомлення транспортів
зберігаються в спільному аудиті; Modbus-логіка та вебпредставлення не змінені.

Перевірка змін лише через mock Telegram/Modbus і синтетичну SQLite:

```bash
.venv/bin/python -m pytest -q tests/test_telegram_fleet.py tests/test_telegram_status_groups.py tests/test_telegram.py tests/test_telegram_controls.py tests/test_telegram_sessions.py
```

Результат оновлення групових команд: **169 Python-тестів пройшли**. Перевірено
25 послідовних mock-команд без дублювання, часткові відмови, повну попередню

Viewer, зміни прав/групи/політики та спільну межу 100.

Міграцій і нових залежностей немає. Застосування після публікації коміту в main,
перевіреного SQLite backup та source/config snapshot потребує погодженого
перезапуску лише наявної служби:

```bash

sudo systemctl is-active ingecon-telegram.service
```

Не запускайте другий polling. Токен і прив’язки не замінюються; production-команди
під час розробки не виконуються. Для відкату повернути попередні `telegram_ui.py`
та `telegram_store.py`, `commands.py` із source snapshot і погоджено перезапустити ту саму службу,
не відновлюючи стару БД поверх нових даних. Production-тег створюється після перевірки активації.

## Залежності

TASK-06 додає aiogram та його залежності до `requirements.txt` і обох lock-файлів.
Наявні Flask/PyModbus-залежності збережені. Використовуйте окреме `.venv`,
описане в README; системний Python не змінюється:

```bash
cd /opt/ingecon-control
.venv/bin/python -m pip install -r requirements-dev.lock
.venv/bin/python -m pip check
```

Для runtime без pytest — `requirements.lock`. Lock-файли фіксують версії без
хешів артефактів. Aiogram/Pydantic/aiohttp встановлено в оточення Python 3.13
через wheel, без встановлення системних пакетів. Flask не імпортує aiogram;
вебпроцес не навантажується моделями Telegram API.

## Явна підготовка схеми та резервна копія

Під час реалізації робоча `instance/database.db` не відкривалась і не мігрувалась.
Не виконуйте наведені команди над робочою БД без погодженої резервної копії та
вікна оновлення. Команди нижче — інструкція майбутнього ручного введення.

Потрібна наявна БД зі схемами TASK-02/03. Вкажіть **той самий абсолютний шлях**,
який використовує вебпанель. Приклад із заповнювачами:

```bash
.venv/bin/python telegram_bot.py prepare-db \
  --database /absolute/path/to/approved.sqlite \
  --backup /absolute/path/to/new-telegram-backup.sqlite
```

`--backup` обов’язковий. Файл резервної копії створюється виключно як новий,
з правами 0600, без перезапису чи переходу за symlink. SQLite backup API робить
узгоджену копію, включно з committed WAL-даними; файл копії не обов’язково
байт-у-байт ідентичний джерелу. Копію потрібно зберігати як секретні дані,
оскільки вона містить наявні облікові записи та збережені паролі інверторів.

Лише після успішного backup створюються сім додаткових таблиць:

- `telegram_link_code`: SHA-256 коду, користувач, версія сесії, строк дії;
- `telegram_link`: числовий Telegram ID, користувач, версія, настройки й курсор подій;
- `telegram_command`: короткочасні підтвердження та знімок цілей;
- `command_audit`: автор, Telegram ID, UTC-час, команда, цілі та результат;
- `telegram_delivery`: окрема доставка кожної події кожному одержувачу;
- `telegram_update`: дедуплікація updates з урахуванням ID бота;
- `telegram_rate`: сталі ліміти запитів і спроб прив’язки.

Таблиці TASK-02/03, інвертори, користувачі, їхні паролі та історія не
перебудовуються. Це додаткова схема, а не універсальний менеджер міграцій.
Після підготовки потрібний контрольований перезапуск вебпроцесу для нової
сторінки `/telegram`; чинний процес не перезавантажується автоматично.

Бот перевіряє всі потрібні таблиці **до Telegram API**. Непідготовлена БД —
відмова запуску, без `create_all` чи автоматичної міграції. Сторінка `/telegram`
також не створює таблиць: без схеми повертає 503 з інструкцією.

## Токен без вихідного коду й shell history

Токен отримує адміністратор у BotFather. Не надсилайте його в чат проєкту,
не додавайте до Git, URL запуску або аргументів командного рядка.

Перший варіант — `INGECON_TELEGRAM_TOKEN` у захищеному середовищі процесу.
Для інтерактивного введення Bash без запису значення в історію:

```bash
read -rsp 'Telegram token: ' INGECON_TELEGRAM_TOKEN
export INGECON_TELEGRAM_TOKEN
```

Другий варіант — приватний файл із самим токеном, одним рядком. Наприклад,
створіть новий `instance/telegram/bot.key` без відображення введеного токена:

```bash
mkdir -p instance/telegram
chmod 700 instance/telegram
.venv/bin/python - <<'PY'
import os
from getpass import getpass
token = getpass('Telegram token: ')
fd = os.open('instance/telegram/bot.key', os.O_CREAT | os.O_EXCL | os.O_WRONLY | os.O_NOFOLLOW, 0o600)
with os.fdopen(fd, 'w') as stream:
    stream.write(token + '\n')
PY
```

Власник файлу має збігатися з користувачем процесу, права — приватні (0600
або суворіші), symlink заборонений. Файл не перезаписується наведеним прикладом.
`instance/` і `*.key` вже ігноруються Git. Одночасно вказувати змінну й файл
не можна: запуск відхиляється. Токен не зберігається у SQLite. Повідомлення
про неправильний токен загальні; logging-фільтр приховує токен і в traceback.

## Ручний запуск і зупинка

Після погодженої підготовки схеми, налаштування секрету й користувачів:

```bash
cd /opt/ingecon-control
.venv/bin/python telegram_bot.py run \
  --database /absolute/path/to/approved.sqlite \
  --token-file /opt/ingecon-control/instance/telegram/bot.key
```

Якщо використовується середовище — приберіть `--token-file`. Зупинка — Ctrl+C
або SIGTERM саме цьому процесу. HTTP-порт не відкривається. Для справжньої роботи
потрібний вихідний HTTPS-доступ до Telegram Bot API; ці команди **не виконувались**
під час розробки, реальний токен не використовувався й повідомлення не надсилались.

Long polling: timeout 25 секунд, HTTP timeout 35 секунд, максимум два HTTP-з’єднання,
лише `message` і `callback_query`, послідовна обробка updates без FSM/Redis.
Окреме асинхронне завдання обробляє сповіщення кожні 5 секунд. Один процес має
працювати з одним токеном. Файлові flock-блокування за БД та ID бота захищають
від другого локального запуску; усі процеси мають використовувати того самого
користувача й `INGECON_LOCK_DIR`. Віддалений інший сервер тим самим flock не
захищається. Наявний webhook спричиняє відмову; код не видаляє його й не очищає
pending updates автоматично. Помилки polling обробляє aiogram з backoff.

Без політики керування блокуються конструктори Modbus-клієнта та NetworkProbes.
Стара політика не знімає нинішнє backend-міжблокування; NetworkProbes блокуються.
Бот не виконує ICMP, TCP-перевірок, Modbus read/write або команд ОС. Вихідні
HTTPS-запити Telegram виконує лише aiogram. Системні служби, Nginx, firewall,
SSH та мережеві налаштування не змінюються.

Архівні тестові SQLite з маркером `demo_metadata` відхиляються до polling.
Інтеграційні тести використовують незалежні синтетичні БД і mock API.

## Прив’язка та відкликання

1. Увійдіть у вебпанель власним користувачем і відкрийте **Налаштування → Telegram** (`/settings/telegram`).
2. Натисніть **Створити код**. POST захищений авторизацією та CSRF.
3. Надішліть `/start КОД` **власному боту в приватному чаті** протягом 5 хвилин.
4. Бот зіставить числовий Telegram user ID із користувачем. Username Telegram
   та довільні ID у тексті команди для авторизації не використовуються.
5. `/start` відкриває меню; `/notifications` дозволяє ввімкнути сповіщення.

Код криптографічно випадковий, 192 біти, у БД зберігається тільки SHA-256.
Він показується лише у відповіді POST, не записується в URL, сесію чи журнал;
GET більше його не показує, відповіді мають `no-store`. Новий код анулює старий.
Споживання атомарне: два одночасні запити не можуть прив’язати його двічі.
Один Telegram ID відповідає одному вебкористувачу і навпаки. Зайнята прив’язка
не перезаписується. Максимум 5 спроб коду на Telegram ID за 300 секунд;
усі updates обмежені 30 за хвилину, ліміти зберігаються в SQLite.

На кожному запиті й перед сповіщенням перевіряються активність, актуальна роль
та версія користувача. Зміна пароля, явне відкликання, деактивація або видалення
користувача закривають доступ бота. Вихід із вебпанелі, вхід іншого користувача,
завершення вебсесії та перезапуск веба/бота не скасовують дійсну прив’язку.
Вихід однією транзакцією відкликає старі вебcookie та зберігає чинну Telegram-прив’язку
й невикористаний код, не змінюючи його строк. Уже недійсні записи не відновлюються.
Для повторної прив’язки відкличте стару у вебпанелі. Кнопка **Відкликати** анулює
також невикористані коди й очікувані підтвердження; queued-доставки пропускаються.
Уже переданий Telegram запит неможливо відкликати заднім числом.

Якщо прив’язка знецінилась через стару поведінку виходу, вкладка Telegram
показує попередження. Потрібно один раз натиснути **Відкликати прив’язку та коди**,
потім **Створити код** і надіслати `/start КОД` своєму боту. Після повторної прив’язки
перевірте налаштування сповіщень. Автоматично відновлювати недійсний запис небезпечно:
неможливо відрізнити старий вихід від відкликання через зміну пароля.
Діагностика, перевірки та застосування виправлення: [TELEGRAM_AUTH_FIX.md](TELEGRAM_AUTH_FIX.md).

Групові/канальні чати, inline callbacks без приватного Message та chat ID,
що не збігається з Telegram user ID, відхиляються до читання даних і прив’язки.
Текст не інтерпретується як HTML/Markdown; previews посилань вимкнені.

## Підтвердження команд і аудит

Спільний `commands.py` містить payload цілей, політику блокування й виконавець,
який використовує вебпанель. Бот звертається до цієї межі через SQLite store;
власних регістрів чи прямих Modbus-викликів у ньому немає.

Вибір інвертора/групи → Start/Stop → точний список ID/назв/IP → остаточне
підтвердження або скасування. Повний список до 100 пристроїв показується за
потреби в кількох повідомленнях, кнопка підтвердження — лише в останньому.
Окремий Telegram-ліміт 10 видалено; використовується та сама межа 100, що й у вебі.
Preview одноразовий і дійсний
120 секунд, прив’язаний до Telegram ID, локального користувача, версії сесії,
ролі, дії та поточного інвентарю. Зміна IP/назви/групи, складу групи, ролі,
видалення цілі чи повторний callback не можуть виконати старе підтвердження.

Остаточне підтвердження атомарно споживає intent і зберігає `processing` перед
викликом спільного сервісу із `source='telegram'`. Потрібні `writes_enabled=True`
та валідна політика: новий спільний дозвіл власника вмикає фіксований 3Play-профіль.
Він не розблоковує довільних чи історичних записів. Mock Modbus виконується без SQLite write lock.
Повторний callback не повторює запис; незавершене виконання після перезапуску
стає `unknown`. Нові конфігурації анулюють старі preview. Вебпанель зберігає
`MODBUS_WRITES_ENABLED=False` без нового дозволу. Інструкція: [CONTROL_ACTIVATION.md](CONTROL_ACTIVATION.md).

`command_audit` зберігає Telegram ID, локальні ID/username, UTC-час, source,
дію, точні цілі та результати по пристроях. Фіксуються preview, підтверджений
blocked, скасування, прострочення, заміна preview, зміна цілей/ролей і відхилені
керувальні callbacks. Секрети, паролі, токени та одноразові коди не записуються.
Повторний callback не створює повторного виконання. Це аудит намірів, відмов і виконання;
результат підтверджує тільки запис регістра, а не фізичний запуск/зупинку.

## Сповіщення й дедуплікація

Сповіщення за замовчуванням **вимкнені**. Власник вмикає їх у меню, вибирає
Online/Offline/Degraded окремо та всі групи або одну групу. Зміна налаштувань
не надсилає накопичений вимкнений backlog. Unknown залишається видимим у
статусі та історії, без окремого сповіщення цього етапу.

Замість глобального `state_event.notified_at` використовуються курсор кожної
прив’язки та unique `(event_id, telegram_id)`. Глобальне legacy-поле залишено
для сумісності TASK-03; воно не може відображати доставку кільком одержувачам.
До 20 прив’язок і по 50 подій на прив’язку за цикл; справедлива ротація курсора.
Не більше одного повідомлення одержувачу за 5-секундний batch, до 20 загалом.
Події до прив’язки, старші 24 годин, вимкнені стани й сторонні групи пропускаються.
Повідомлення містить ID події, історичний перехід і київський час (`Europe/Kyiv`); це не нове опитування.

Доставка: pending → sending (commit до HTTP) → sent із Telegram message ID.
Повторний цикл, restart або повторна поява тієї самої події не дублюють sent.
Перед відправленням знову перевіряються права й настройки; SQLite-транзакція
не утримується під час очікування Telegram API.

- Підтверджений Telegram 429: retry_after, максимум 5 спроб, без раннього повтору.
- Forbidden: failed, сповіщення цього користувача вимикаються.
- Bad Request: failed, без автоматичного повтору.
- Timeout/обрив/невизначена API-помилка: unknown, без автоматичного повтору.
- Аварійно залишений sending після restart: unknown, без автоматичного повтору.

Telegram sendMessage не має ключа ідемпотентності. Після загубленої відповіді
неможливо довести, чи повідомлення прийнято; одночасно гарантувати доставку
та відсутність дубля не можна. Обрано консервативну дедуплікацію: unknown
потребує перегляду адміністратором, автоматичної повторної відправки немає.
Командний журнал і вебісторія залишаються джерелом перевірки.

Updates дедуплікуються за `(bot ID, update_id)` до handler, у SQLite. Після
падіння всередині handler update автоматично не відтворюється: чутливу дію
потрібно почати заново. Новий підтверджувальний callback додатково захищений
одноразовим intent. Payload updates не зберігається.

## RAM, eMMC та обслуговування

Один процес, до двох одночасних HTTP-з’єднань, послідовні handlers, без постійної FSM
чи копії інвентарю в RAM. SQLite-вибірки історії/списків/сповіщень обмежені;
загальний статус, як і чинний веб API, читає весь невеликий парк інверторів.
Idle polling не додає рядків журналу кожні 5 секунд; курсор змінюється лише
за нових подій. Запити до Telegram не тримають транзакцій або DB connection.

Раз на годину cleanup видаляє не більше 1000 рядків кожного допоміжного типу:
updates старші 7 днів, давно прострочені rate buckets, прострочені коди,
intents старші доби й завершені доставки старші 30 днів. Аудит команд та
історія станів автоматично не видаляються. Перед тривалою експлуатацією на
8 ГБ eMMC потрібна погоджена політика архівування аудиту/історії та контроль
обсягу БД. Автоматичного VACUUM, cron, journald/systemd чи logrotate цей етап
не налаштовує. Дискові розміри й RAM production-навантаження не вимірювались.

## Перевірки без реального Telegram

```bash
cd /opt/ingecon-control
.venv/bin/python -m pytest -q tests/test_telegram.py
.venv/bin/python -m pytest -q
node tests/js/dashboard.test.cjs
node tests/js/panel.test.cjs
.venv/bin/python -m pip check --disable-pip-version-check --no-cache-dir
git diff --check
```

`FakeTelegramSession` реалізує aiogram BaseSession в пам’яті. Тести подають
справжні aiogram Update через Dispatcher, перехоплюючи SendMessage,
AnswerCallbackQuery, GetWebhookInfo та SetMyCommands; GetUpdates/polling
підставлений у перевірці запуску. Справжніх Telegram API-запитів немає.
Загальна фікстура забороняє IP socket/connect/DNS і subprocess.run; для
asyncio дозволено лише обгортання вже створених AF_UNIX socketpair-дескрипторів
внутрішнього waker. Це не IP-з’єднання. Modbus залишається in-memory mock.

Перевіряються прив’язка/гонки/expiry/replay, CSRF і ролі вебсторінки, приватні
чати, усі команди та кнопки, пагінація, stale/heartbeat, підміна цілей/ролей,
одноразовість підтвердження, blocked-аудит, opt-in/групи/стани сповіщень,
дедуплікація кількох одержувачів, 429/timeout/Forbidden/restart, token redaction,
backup із WAL та відмова непідготовленої або архівної тестової БД до polling.

Результат TASK-06: **408 Python-тестів пройшли**, з них **76 Telegram-тестів**;
xfailed і попереджень pytest немає. **17 JS-тестів пройшли**. `pip check`
та `git diff --check` успішні. Розмір і час зміни робочої БД та робочого журналу
залишились незмінними. Реальні Modbus-операції й Telegram API не виконувались.
